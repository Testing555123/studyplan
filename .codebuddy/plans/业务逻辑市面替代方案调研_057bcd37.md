## 用户需求

为 StudyPlan 重建项目（Next.js 16 + React 19）中"明确必须自研"的核心业务逻辑，全面寻找市面上的可替代方案，判断能否削减或消除自研工作量。

## 调研边界（已与用户澄清确认）

- **范围**：仅当前核心业务逻辑 = `docs/SPEC.md` / `docs/TECH-SELECTION.md` 表格中"必须自研"的一行，即：帖子/评论/点赞数据模型与 Server Actions、RAG 检索编排、Agent loop。不含未来批次（GitHub 趋势、每日推荐、AI 助手 UI、学习路线、面试题）与已落地资产（电子书、本地嵌入/重排）。
- **替代类别**：两者都找（最全面）。既覆盖具体功能级（评论系统、搜索/向量库、RAG/Agent 框架、AI 托管 API），也覆盖整栈/平台级（Supabase、Convex、Payload、Discourse 等整体承载）。
- **交付形式**：作为补充章节更新进现有 `docs/TECH-SELECTION.md`，与既有选型结论并列，不新建文件、不只在对话输出。

## 评估标尺与硬约束（来自 SPEC/DECISIONS）

- 标尺：全生命周期成本（开发+调试+长期维护），自研量越接近 0 越好，自研部分应是"产品本身"而非横切关注点。
- 单容器 Vercel Container Runtime（`output: 'standalone'`，Node 24 alpine），禁止多进程/多容器。
- PostgreSQL 16 + pgvector + Drizzle；better-auth 会话（HttpOnly Cookie，业务表仅外键引用 user id）。
- SSR/SEO 硬要求：评论/内容必须进 HTML，不得 iframe 无 SEO。
- 评论为 posts 一对多、计数与帖子强一致、删除权限绑定 better-auth 会话；计数原子化（`GREATEST(0,...)` 兜底）。
- 可选能力（AI/模型/检索）不可用时必须降级不阻断启动。

## 核心目标

复核既有"业务层无现成方案、必须自研"（§8）与本地 Qwen3 全套（§9）结论，补齐被遗漏候选，对每个候选给出 stars / license / last push / 约束冲突 / 结论，并最终裁定"维持自研 / 可部分替换 / 可整体替换"。

## 调研方法论

1. **边界固化**：先精读 `lib/embeddings.ts`、`lib/rerank.ts`、`lib/source.ts` 与 `docs/SPEC.md`、`TECH-SELECTION.md`、`DECISIONS.md`，把"必须自研"的三块（帖子/评论/点赞、RAG 检索编排、Agent loop）拆成可逐项替换的最小单元，形成约束清单。
2. **实时核实**：对全部候选用 web 检索获取**当日** stars / license / last push（既有 §8 数据停留在 2026-10-09，需刷新，尤其 Payload v4 是否已发稳定版、Supabase 单容器约束是否真冲突）。
3. **约束对比矩阵**：逐候选对照单容器 / PG+pgvector / SSR+SEO / better-auth / 全生命周期成本五维，判定兼容性与工作量削减幅度。
4. **文档落盘**：在 `docs/TECH-SELECTION.md` 新增补充章节（建议"§12 业务逻辑自研点的市面替代方案复核"），保留 §8/§9 作为对比基线，避免覆盖既有结论。

## 候选覆盖清单

- **A. 具体功能级**：评论/互动（Giscus、Waline、Artalk、Utterances、Hyvor Talk、Commento++、ReplyBox、Disqus、Remark42、Cusdis、Staticman）；搜索/向量库（pgvector 现有、Meilisearch、Typesense、Algolia、Vespa、Pinecone、Weaviate Cloud、Qdrant Cloud、Zilliz、Chroma Cloud、Neon/Supabase Vector、Redis Stack）；RAG/Agent 框架（Vercel AI SDK 已选、LangChain.js、LlamaIndex.ts、Mastra、CopilotKit、LangGraph.js、DSPy.ts、Haystack、RAGFlow）；AI 托管 API（OpenAI、DeepSeek、通义/百炼、智谱 GLM、Kimi、SiliconFlow、Together、Groq、Ollama、vLLM；嵌入/重排托管 Voyage AI、Jina Embeddings、Cohere Rerank、Mixedbread）。
- **B. 整栈/平台级（重新评估排除理由）**：Supabase、Convex、Payload v4、Strapi、Directus、PocketBase、NocoBase、Keystatic、ZenStack、tRPC+Prisma、RedwoodJS、Wasp、Blitz、t3 stack；社区平台级 Discourse、Flarum、Ghost、NodeBB。

## 重点复核点

- 既有 §8 仅评估 3 个评论系统，需补满候选并验证"能否进自有 PG、与 posts 强一致计数、SSR、绑定 better-auth"。
- 本地 Qwen3 600MB q8 包袱（冷启动 36s/71s、主线程阻塞）vs 托管嵌入/重排 API 的成本/延迟权衡。
- 整栈排除理由"品类错配 / 单容器冲突"是否仍成立——重点复核 Payload v4 稳定版状态、Supabase 是否真需多容器、Discourse 能否作为 C 端社区整体替代。

## 可靠性与避免返工

- 所有 stars/license/last push 必须当日 web 核实，标注核实日期，不沿用 §8 旧数据。
- 每个排除/保留结论都要落到具体约束冲突条目，便于后续回溯。
- 不删除/改写既有 §8/§9，只在新增章节给出"裁定（维持/可部分替换/可整体替换）"，保证历史决策可追溯。
