## 二、核心概念

### 1. LLM 的输出就是"外部输入"

这是本阶段最重要的一句话。用户提交的表单不可信，**模型的返回同样不可信**：

- 它可能先说一句"好的，这是结果："再给 JSON；
- 可能用 Markdown 代码块把 JSON 包起来；
- 可能把 `summary` 写成 `Summary`；
- 可能返回 8 个标签（你只要 5 个）；
- 可能把"一句话摘要"写成 300 字；
- 可能编造一个不在白名单里的标签（把 `Vue` 写成 `Vue3`）。

**前三个是"格式不对"，后三个是"格式对但内容不合规"。**
两类都必须拦住 —— 而"内容不合规"这类最危险，因为它**不会报错**，
只会让数据库里悄悄多一条奇怪的数据。

#### 实现方法

本项目把 AI 返回的 `summary`、`tags` 当成不可信输入，先过 `sanitizePostMeta` 清洗（剥离 Markdown 代码块、统一字段名、过滤非法标签），再入库。任何"模型应该会返回 JSON"的假设都不成立。

#### 原理

模型输出是概率生成，不是确定性函数：它会加前缀、套代码块、改名、超量、编造白名单外的标签。前三类是"格式不对"，后三类是"格式对但内容不合规"，后者尤其危险，因为它不报错，只会在库里悄悄多一条脏数据。对待模型输出要像对待用户表单一样先校验。

#### 与相关技术栈的关系

和"正则切割文本"相比，结构化输出用 Schema 约束形状；但两者都不解决"内容不合规"，后者必须靠代码兜底。和传统的"信任第三方接口"相比，LLM 的不确定性更高，更需要防御性解析。和后端从不可信客户端收数据的原则一致：永远先校验再使用。

#### 面试常见问题与解题思路

**Q1：为什么 LLM 的输出要当外部输入处理？**
怎么想：从"非确定性"切入。怎么答：模型可能加前缀、套代码块、改字段名、编假标签，必须像校验表单一样先清洗再入库。追问：光靠 Prompt 要求"只返回 JSON"够吗？

**Q2：结构化输出失败时要怎么兜底？**
怎么想：从"降级"切入。怎么答：解析失败返回 null、记 warn、走默认分支，不让 AI 失败拖垮主流程。追问：哪些失败是静默的、最难发现？

### 2. 结构化输出：从"祈祷"到"验证"

```ts
// ❌ 把输出当成给人看的文本，再用字符串切割去解析
const [summary, ...tags] = (text.content as string).split('，')

// ✅ 把输出当成接口契约
const schema = z.object({
  summary: z.string().min(1).max(200),
  tags: z.array(z.string()).min(1).max(MAX_TAGS_PER_POST),
})
const result = await model.withStructuredOutput(schema).invoke(messages)
```

> Prompt 是**建议**，Schema 是**校验**。
> 模型可以无视建议，但无法让不符合 Schema 的结果通过校验。

**但不要因此以为 Schema 一定成功。** 不同模型对结构化输出的支持程度不同，
所以解析失败的分支仍然必须存在。

#### 实现方法

本项目用 `model.withStructuredOutput(schema)` 让模型按 schema 返回对象，Schema 里约束 `summary` 长度、`tags` 数量上限（上限常量来自 `@studyplan/shared`）。Prompt 写"建议"，Schema 做"校验"，解析失败回退到 null。

#### 原理

结构化输出把"祈祷它能返回 JSON"变成"强制它过了校验才接受"。模型可以忽略 Prompt 建议，却无法让不符合 Schema 的结果通过校验。但不同模型对结构化输出的支持程度不同，有的会忽略、有的会偏离，所以解析失败的分支仍然必须存在，不能假设 Schema 一定成功。

#### 与相关技术栈的关系

和手写 JSON.parse 加 try/catch 相比，结构化输出由 SDK 统一处理提示词与解析，更省事。和 OpenAI 的 function calling、tool use 同源：都是用 schema 约束 LLM 输出。和 JSON Mode（仅要求返回合法 JSON）相比，带 schema 的版本还能校验字段类型与范围。zod、Pydantic 是常见 schema 描述方式。

#### 面试常见问题与解题思路

**Q1：Prompt 和 Schema 各自解决什么？为什么都要？**
怎么想：从"建议 vs 校验"切入。怎么答：Prompt 是软建议，Schema 是硬校验；模型可无视建议但不能绕过校验。追问：只写 Prompt 不写 Schema 有什么风险？

**Q2：结构化输出一定能拿到合法 JSON 吗？**
怎么想：从"模型差异"切入。怎么答：不一定，不同模型支持度不同，必须保留解析失败分支。追问：失败时要怎么处理才不拖垮主流程？

### 3. 能力的边界：Schema 管形状，代码管取值

`tags` 的 Schema 只约束了"是 1-5 个字符串"，**没有**约束"必须是白名单里的值"。

为什么？因为把 10 个标签白名单塞进 Schema 描述会让 Prompt 变得啰嗦，
而且模型仍然可能不遵守。而"过滤非法标签"是纯逻辑 ——
放在代码里更可靠，也更好测试。

> 一条经验：**能用代码确定的规则，不要交给模型去遵守。**

#### 实现方法

本项目 `tags` 的 Schema 只约束"1-5 个字符串"，具体的白名单过滤放在 `sanitizePostMeta` 里：过不了白名单的标签直接丢弃。代码层负责"值是否合法"，Schema 层负责"形状是否合法"。

#### 原理

把 10 个标签白名单塞进 Schema 描述有两个问题：让 Prompt 变啰嗦，且模型仍可能不遵守。而"过滤非法标签"是确定性纯逻辑，放在代码里更可靠、也更好测试。能用代码确定的规则，不要交给模型去遵守。

#### 与相关技术栈的关系

和"在 Prompt 里穷举允许值"相比，代码过滤更稳、更易测、更易演进。和数据库约束（如枚举字段）相比，这里在应用层清洗后再入库，适合"来源不可信"的模型输出。这条经验也适用于普通外部输入：允许集校验放代码，形状校验放 schema。

#### 面试常见问题与解题思路

**Q1：为什么标签白名单校验放在代码里而不是 Schema？**
怎么想：从"确定性"切入。怎么答：白名单是确定逻辑，代码执行 100% 可靠且好测；塞进 Prompt 模型可能不遵守。追问：Schema 该管到什么程度？

**Q2：模型输出清洗一般包含哪些步骤？**
怎么想：从"防御解析"切入。怎么答：去代码块或前缀、统一字段名、按白名单过滤、按长度裁剪、空值兜底。追问：为什么"空摘要"也要当失败处理？

### 4. 超时：两层保证，缺一不可

```ts
const controller = new AbortController()
const timeout = new Promise((_, reject) => {
  timer = setTimeout(() => {
    controller.abort()                 // ② 尽力真正取消底层请求
    reject(new Error('调用超时'))
  }, timeoutMs)
})
return await Promise.race([task(controller.signal), timeout])   // ① 保证应用层一定往下走
```

- **① `Promise.race` 是硬保证**：不管底层请求有没有真的结束，
  我们的代码在 `timeoutMs` 之后一定会继续走。这是"不阻塞主流程"的底线。
- **② `AbortController` 是尽力而为**：它能不能真正取消，取决于第三方库
  有没有把 `signal` 透传下去（本项目已核实 `ChatZhipuAI` 确实透传了）。

**为什么不能只做 ②？** 因为"能不能取消"是别人的实现细节，
而"不阻塞"是我们必须自己保证的。

> 依赖别人的承诺，不如自己兜底。

#### 实现方法

本项目用 `Promise.race([task(signal), timeout])` 保证应用在 `timeoutMs` 后一定继续；`timeout` 内部 `controller.abort()` 尽力取消底层请求。两层都写，缺一不可，超时阈值来自 `NVNIM_TIMEOUT_MS`。

#### 原理

`Promise.race` 是硬保证：无论底层请求结束与否，我们的代码在超时后一定往下走，这是"不阻塞主流程"的底线。`AbortController` 是尽力而为：它能否真正取消，取决于第三方库有没有把 `signal` 透传下去。只做 abort 不够，因为"能不能取消"是别人的实现细节，而"不阻塞"必须自己保证。

#### 与相关技术栈的关系

和单一 `setTimeout` 相比，race 才能强制应用层推进；和 axios 的 `timeout` 选项相比，手动 race 更可控、能同时做取消。和后端网关或反向代理的超时（如 Nginx `proxy_read_timeout`）相比，应用层超时负责"单个调用不拖垮请求"，网关超时负责"整体不卡死"。

#### 面试常见问题与解题思路

**Q1：为什么需要 Promise.race 和 AbortController 两层？**
怎么想：从"硬保证 vs 尽力"切入。怎么答：race 保证不阻塞，abort 尽力取消；只做一层都不保险。追问：只做 abort 会有什么后果？

**Q2：AbortSignal 真的能取消请求吗？**
怎么想：从"透传"切入。怎么答：取决于库有没有把 signal 传到底层 fetch 或网络；本项目已核实 ChatZhipuAI 透传了。追问：怎么验证一个库确实透传了 signal？

### 5. 旁路：为什么不用 `await`

```ts
const contract = toPostContract(...)
void this.enrichWithAi(contract.id, dto.title, dto.content)   // ← 故意不 await
return contract
```

如果写成 `await`，会发生三件坏事：

1. 用户点"发布"后要**等模型想完**才跳转（2-15 秒），
   而这跟他的目标（把文章发出去）毫无关系；
2. 模型服务慢，用户就得一直等；
3. **模型服务挂了，用户就发不出文章** —— API Key 失效、限流、网络抖动，
   全都变成了"发帖失败"。

> 一句话：**await 一下，AI 就从"增强功能"变成了"核心链路的单点故障"。**

#### 实现方法

本项目发帖成功、数据库落库后，用 `void this.enrichWithAi(...)` 故意不 await，立刻 `return contract`。用户点发布后立刻跳详情页，AI 摘要随后异步回填。401 静默续期重放时也因不 await 而安全。

#### 原理

若写成 `await`，用户要等模型想完（2-15 秒）才跳转，与"把文章发出去"的目标无关；模型慢就跟着慢；模型挂了用户就发不出文章。一句话：await 一下，AI 就从"增强功能"变成了"核心链路的单点故障"。`void` 显式表达"故意不等"，避免被 lint 误判为漏写。

#### 与相关技术栈的关系

和"同步处理链路"相比，旁路用异步 fire-and-forget 把非核心工作从关键路径剥离。和消息队列（把任务扔给后台 worker）相比，`void` 是最轻量的本地旁路，适合"失败了也不要紧"的场景。和事件驱动（发事件让别的模块订阅）相比，直接调用更直白，但耦合更紧。

#### 面试常见问题与解题思路

**Q1：为什么 AI 摘要要用 void 而不是 await？**
怎么想：从"核心链路 vs 增强功能"切入。怎么答：await 会让 AI 成为发帖的单点故障，且不必要地拖慢用户。追问：void 有什么讲究？为什么不用省略 await？

**Q2：旁路调用失败会怎样？怎么保证不影响主流程？**
怎么想：从"异步隔离"切入。怎么答：不 await 使失败脱离请求链路；被调方把错误转成返回值（null）并兜底 try/catch，避免未处理 Promise 拒绝。追问：什么场景适合 fire-and-forget？

用 `void` 明确表达"我故意不等它"，比偷偷省略 `await` 好 ——
后者会被 lint 警告，也会让读代码的人以为你忘了。

### 6. 依赖必须存在吗？这是产品判断

| 依赖 | 缺失时的行为 | 为什么 |
| --- | --- | --- |
| `MONGODB_URI` | **拒绝启动**（fail fast） | 数据库是核心依赖，没有它后端没有意义 |
| `NVNIM_API_KEY` | 降级运行 + 日志提示 | AI 是增强功能，没有它应用依然完整可用 |

把增强功能也做成硬依赖，等于用一个可选项卡住了整个系统 ——
新人第一次跑项目时，会因为没填一个他根本不需要的 Key 而完全跑不起来。

**"哪些依赖必须存在"是一个产品判断，不是一个技术判断。**

#### 实现方法

本项目 `MONGODB_URI` 缺失就 `fail fast` 拒绝启动；`NVNIM_API_KEY` 缺失则降级运行并记"功能已停用"提示。判断依据是"它是不是核心功能"，不是技术。

#### 原理

把增强功能（AI）也做成硬依赖，等于用一个可选项卡死了整个系统：新人第一次跑项目会因没填一个他根本不需要的 Key 而完全跑不起来。"哪些依赖必须存在"是一个产品判断，不是技术判断：核心依赖缺失就该立即失败给明确信号，可选依赖缺失应优雅降级。

#### 与相关技术栈的关系

和"所有依赖缺失都拒绝启动"相比，分级处理让可选项不阻塞核心。和 Kubernetes 的 `liveness`/`readiness` 探针相比：`fail fast` 对应启动即崩，`readiness` 可对应"AI 模块未就绪但服务可用"。和 Feature Flag 相比，本项目用"环境变量是否配置"作为功能开关，更简单。

#### 面试常见问题与解题思路

**Q1：为什么有的依赖缺失要 fail fast，有的要降级？**
怎么想：从"核心 vs 增强"切入。怎么答：缺核心依赖系统无意义，立即失败清晰；缺增强功能应降级保主流程。追问：降级时怎么让用户或运维知情？

**Q2：fail fast 有什么好处？**
怎么想：从"早暴露"切入。怎么答：把配置错误在启动期暴露，而不是运行时偶发崩溃，排查成本低得多。追问：和"启动尽量宽容"相比，什么场景该宽容？

### 7. 选模型看"产出速度"，不看名字

默认模型叫 `deepseek-ai/deepseek-v4-flash-0731`，名字里有 "flash"。
但实测它的返回结构是：

```text
content=58字   reasoning=508字   completion_tokens=316
```

它是**推理模型**：先写一大段思考链，再产出很短的答案。
简单问题 22 秒，问题一复杂就直接撞上超时上限 ——
**"flash" 只描述它的定位，不代表延迟低。**

同一段中文问答 prompt 的实测对比：

| 模型 | 耗时 | 产出正文 | 思考链 |
| --- | --- | --- | --- |
| `openai/gpt-oss-20b` | 20.6s | 747 字（≈ **36 字/秒**） | 339 字 |
| `google/gemma-4-31b-it` | 25.4s | 590 字（≈ 23 字/秒） | 0 |
| `deepseek-ai/deepseek-v4-flash-0731` | 22s（简单问题） | 58 字 | **508 字** |
| `z-ai/glm-5.3-flash` | **>70s 超时** | — | — |
| `meta/llama-3.3-70b-instruct` | **410 Gone** | — | — |

**关键指标不是"总耗时"，而是"产出速度"（正文字数 ÷ 秒）** ——
因为超时只跟"要生成多少字"有关，而总耗时里还混着排队与首字延迟。

同理，`max_tokens` 也不只是"限制答案长度"：
对推理模型来说它要**同时装下思考链与正文**，
所以它直接决定了**最坏等待时间**。

#### 实现方法

本项目默认模型名走 `NVNIM_MODEL` 环境变量、不写死，并在遇到 410 或 404 时把上游语义翻译成"请在 NVNIM_MODEL 换一个可用模型"。选型时看"正文字数 ÷ 秒"而非总耗时。

#### 原理

"flash"只描述定位，不代表延迟低；推理模型先输出一大段思考链再给短答案，总耗时被思考链撑大，但超时只跟"要生成多少正文"有关。所以关键指标是正文产出速度，而 `max_tokens` 对推理模型还要同时装下思考链，直接决定最坏等待时间。

#### 与相关技术栈的关系

和"按模型名气或宣传选模型"相比，按实测产出速度选型更贴近产品体验。和只用总耗时评估相比，区分"排队或首字延迟"与"正文生成速度"能更准地预测超时风险。和把模型名写死相比，可配置模型名让"模型下线"从故障变成一次环境变量变更。

#### 面试常见问题与解题思路

**Q1：选 LLM 该看什么指标？为什么不是总耗时？**
怎么想：从"超时来源"切入。怎么答：超时只跟要生成的正文量有关，总耗时混入排队与首字延迟；看产出速度更准。追问：推理模型的 max_tokens 为什么更敏感？

**Q2：模型名为什么要做成配置？**
怎么想：从"会变的标识"切入。怎么答：模型会下线（410），写死会在某天无声失效；配成变量并翻译上游错误，让更换变成一次配置。追问：怎么把上游错误翻译成用户可操作提示？

## 三、代码走读

### `ai.service.ts` —— 一个"永远不抛异常"的类

```ts
async generatePostMeta(input): Promise<AiPostMeta | null>
```

所有失败都返回 `null`。为什么？

因为它的调用方是"发帖"这条核心链路。如果 AI 失败会抛异常，
那么每一个调用点都要写 try/catch —— 写漏一处，用户的文章就发不出去了。

**把"失败"表达成返回值而不是异常，是旁路组件的标准做法：**
异常是给"必须处理的问题"用的，而 AI 失败不是必须处理的问题。

它也不依赖任何数据库模块 —— 回填落库由 `PostsService` 做。
这样依赖方向是单向的（posts → ai），不会形成循环依赖。

### `posts.service.ts` 的 `enrichWithAi`

三层保险，让旁路绝不影响主链路：

1. `generatePostMeta` 自己已经把所有失败转成了 `null`；
2. 这里再包一层 `try/catch`，兜住"回填落库"可能出现的数据库错误；
3. 整体不 `await`，所以即使真的抛了，也已经脱离请求链路。

第 2 层不能省 —— 否则一个未处理的 Promise 拒绝可能让进程告警甚至退出。

### `utils/post-meta.sanitizer.ts` —— 为什么把纯逻辑拆出来

`sanitizePostMeta` 是一段**纯函数**：给同样输入永远给同样输出，
不依赖网络、不依赖配置、不依赖时间。

而它所在的 `AiService` 里全是网络 I/O。混在一起的结果是：
**这段最需要测试的逻辑反而测不了**（要测它就得先 mock 一个 HTTP 客户端）。

拆出来之后，它有 9 个边界用例覆盖，跑一次几十毫秒。

> 一条很实用的重构经验：**把"纯逻辑"从"有副作用的方法"里拔出来。**
> 这是提升可测试性性价比最高的一个动作。

### `ai.module.ts` —— 空 imports 是刻意的

```ts
@Module({ providers: [AiService], exports: [AiService] })
export class AiModule {}
```

它不 import `PostsModule`，所以依赖是单向的。

如果反过来（`AiModule` 也 import `PostsModule`），就形成了**循环依赖**，
NestJS 会要求你用 `forwardRef()` 包起来 ——
而 `forwardRef` 是一个明确的信号：**你的模块边界划错了**。

> 遇到循环依赖时，不要第一反应去加 `forwardRef`，
> 先问："是不是有一个东西的职责放错了位置？"
> 本项目里答案是"回填应该由数据的拥有者（帖子模块）来做"。

## 四、踩坑记录

### 坑 1 · 官方文档说"已弃用"，但代码里其实还在

查接入方式时，找到的文档页顶部明确写着"随 LangChain v1.0 发布而弃用，不再维护"，
里面给的路径是 `@langchain/community/chat_models/zhipuai`。

于是产生了两个不确定：
1. 这个包还在不在（项目用的是 `@langchain/community@1.1.29`）？
2. 这个导入路径还有效吗？

**没有靠猜，而是装完之后直接去文件系统里找**：

```text
apps/api/node_modules/@langchain/community/chat_models/zhipuai.js      ← 存在
apps/api/node_modules/@langchain/community/chat_models/zhipuai.d.ts    ← 存在
package.json 的 exports 里能找到 zhipuai                              ← 有效
```

结论：文档虽然标的 v0.3 分支，但这个集成在 v1 里**仍然存在且可用**。

> **文档的版本标记会过期，文件系统不会。**
> 涉及"某个 API 到底还在不在"这类问题时，直接去 `node_modules` 里看，
> 比读文档快、也比读文档准。

顺带确认了 `withStructuredOutput` 存在（且支持 zod 4），
以及 `ChatZhipuAI` 确实把 `options.signal` 透传到了底层 `fetch` ——
后者决定了超时能不能真正取消请求，光看文档是看不出来的。

### 坑 2 · "调用成功但结果不可用"是最危险的失败

写完之后意识到一个问题：**AI 的失败不止"报错"一种**。

| 失败形态 | 会不会报错 | 会不会被日志发现 |
| --- | --- | --- |
| 网络超时 | 会 | 会 |
| 鉴权失败 | 会 | 会 |
| 返回非法 JSON | 会 | 会 |
| **标签全不在白名单** | **不会** | **不会**（除非专门记一条） |
| **摘要为空字符串** | **不会** | **不会** |

后两种才是真正危险的：它们不抛异常、不超时，日志里一切正常，
只是数据库里悄悄少了一个摘要。

所以 `sanitizePostMeta` 返回 null 时，**单独记了一条 warn**：

```ts
this.logger.warn(`AI 返回内容不可用，已跳过（耗时 ${...}ms）`)
```

没有这一行，你会永远不知道"为什么有 30% 的帖子没有摘要"。

### 坑 3 · AI 标签不能直接合进作者选的标签

最初的打算是"把 AI 推荐的标签合并进 `post.tags`"，理由是省掉一个字段。

但它有一个无法接受的问题：**作者意图与机器建议混在一起之后，
用户就无法表达"我不要这个标签"** ——
他也分不清"这篇文章被归类为 Vue，是作者认为如此，还是模型猜的"。

所以给契约加了一个**可选字段** `aiTags`。这正好是本项目第一次做"契约演进"，
套路值得记住：

```text
加可选字段 ＞ 改字段名（要两端同时改）＞ 加必填字段（尽量避免）
```

加可选字段是**向后兼容**的：旧代码不读它，一切照常。

### 坑 4 · 新增一个依赖，所有已有测试文件都要改

`PostsService` 新增了 `AiService` 依赖之后，`posts.service.spec.ts` 立刻报错：

```text
Nest can't resolve dependencies of the PostsService (..., ?)
```

必须给测试模块补上 `{ provide: AiService, useValue: {...} }`。

**这就是依赖注入的代价之一：每加一个依赖，测试脚手架就要跟着改。**
但它换来的是"依赖关系显式可见" —— 而不是藏在构造函数里的 `new`。
后者的问题在于：你永远不知道改一个类的内部实现会影响谁。

测试里把替身设成 `enabled: false`，于是发帖后的 AI 增强会立刻返回，
不会产生任何真实网络调用 —— 这也是"依赖可替换"带来的直接好处。

### 坑 5 · 正文不能全文送给模型

三个理由，每个都实际：

1. **成本**：token 按量计费，万字长文全文送去会明显变贵；
2. **延迟**：输入越长响应越慢，而超时上限是固定的；
3. **收益极低**：摘要与标签的判断依据几乎全在开头部分。

所以 `buildPostMetaPrompt` 里做了 4000 字符截断，并在截断时
在 Prompt 里**明确告诉模型**"以上为开头部分" ——
不告诉它的话，它可能会写出"本文未讨论…"这类判断失误的摘要。

### 坑 6 · 模型会下线，所以模型名不能写死

本次实测中，**三个**模型返回 `410 Gone`：

```text
The model 'meta/llama-3.1-8b-instruct' has reached its end of life
on 2026-08-26T09:00:00Z and is no longer available.
```

（写这段注释期间又接连踩到 `nvidia/nemotron-3-nano-30b-a3b`、`meta/llama-3.3-70b-instruct`）

所以模型名必须**可配置**（`NVNIM_MODEL`），并且在遇到 410/404 时，
把上游语义**翻译成能直接照做的提示**：

```text
模型「xxx」已下线或不存在，请在环境变量 NVNIM_MODEL 中更换一个可用模型
```

而不是把 `410` 原样甩给用户 —— 用户看到状态码只能猜。

> **凡是"会变的标识"都该做成配置**：模型名、API 版本、端点。
> 写死的时候它一定能用，问题只在"哪天突然不能用了" —— 而且不会有任何预警。

### 坑 7 · 构建期产物只写在一处，本地就永远拿不到

AI 学习助手要回答"这段本站代码为什么这样写"，靠的是一份
**构建期生成的代码索引**（运行层没有源码，所以只能这么做）。

但生成它的那一步**只写在 `Dockerfile.vercel` 里**：

```dockerfile
RUN pnpm --filter @studyplan/api build
RUN node scripts/generate-code-index.mjs   # ← 只有容器构建会执行这一行
```

于是本地 `pnpm build` 不会生成索引 → 检索不到任何文件 →
AI 回答退化成"资料中没有提到"。**不报错、不崩溃**，只是悄悄变笨。

修法是把这一步并进包自己的构建脚本，让本地与容器走同一条路径：

```json
"build": "nest build && node ../../scripts/generate-code-index.mjs"
```

> 同一个动作被写在两个地方（Dockerfile 一份、"本该在" package.json 一份），
> 就是这类 bug 的温床。
> **只要一个步骤在「本地」和「线上」走的是不同代码路径，它们迟早会分叉。**

顺带补了一处可观测性：索引加载原本是"第一次提问时才惰性加载"，
现改为**启动即预热** —— 缺文件会在启动日志里立刻显示，
而不是等用户问出一个答不出的问题之后才去猜为什么。

## 六、术语表

| 术语 | 一句话解释 |
| --- | --- |
| 结构化输出 | 用 Schema 约束模型返回的 JSON 形状 |
| Prompt 模板 | 把任务描述、约束、输入拼成一次调用的文本 |
| 降级 | 次要功能失败时不让主要功能受影响 |
| 旁路 | 不参与主流程、失败也不影响主流程的调用 |
| 超时双保险 | Promise.race 保证不阻塞 + AbortSignal 尽力取消 |
| 脱敏 | 日志里把敏感值替换掉 |
| 循环依赖 | 两个模块互相依赖，Node 里通常意味着职责划分有问题 |
| 契约演进 | 在保持向后兼容的前提下修改接口定义 |
| 静默失败 | 不报错、不告警，只是结果不对 |
| 截断 | 把超长输入裁短，控制成本与延迟 |
