# 阶段 8 · 测试与上线

> 前面七个阶段，运行环境只有一个：**你自己的电脑**。
> 这一阶段要面对一个全新类型的问题 —— **"在我机器上是好的。"**

---

## 一、验收清单

### 端到端测试

前置：**三样东西都得在跑**（Atlas 可达、`pnpm dev:api`、`pnpm dev:web`）。

```bash
# 首次需要下载浏览器（只需一次，约 100MB）
pnpm --filter @studyplan/web exec playwright install chromium

# 跑 E2E
pnpm --filter @studyplan/web e2e

# 想看浏览器里到底发生了什么
pnpm --filter @studyplan/web e2e:headed
```

- [ ] 6 条用例全部通过
- [ ] **再跑一遍，仍然全部通过**（这一条最重要，见下文"可重复性"）
- [ ] 故意改坏一个断言（比如把标题写错）→ 确认它**真的会失败**
- [ ] 失败时生成了 `trace` 文件，能回放整个操作过程

### 部署

- [ ] 电子书有可访问的线上地址
- [ ] 前端有可访问的线上地址
- [ ] 线上能完整走通一次：注册 → 发帖 → 评论 → 点赞
- [ ] `NUXT_PUBLIC_API_BASE` 指向线上后端，而不是 `localhost`
- [ ] `CORS_ORIGIN` 包含前端线上域名，而不是本地地址
- [ ] `COOKIE_SAME_SITE=none`（跨域时），且后端是 HTTPS
- [ ] `NODE_ENV=production`（否则 `secure` Cookie 不会生效）
- [ ] 把 `E2E_BASE_URL` 指向线上地址跑一次 E2E → 通过

> 最后一条是整本书的收尾：**用同一套测试验证线上环境**。
> 它同时证明了"部署成功"和"测试可信"。

## 二、核心概念

### 1. 单测与 E2E 不是替代关系，是互补关系

| | 单元测试（阶段 3-7 的 Jest） | 端到端（这个阶段） |
| --- | --- | --- |
| 跑的是什么 | 你的逻辑，数据库和网络都被替身换掉 | **真实系统**：真实浏览器、真实请求、真实数据库 |
| 速度 | 几秒跑几十个 | 几十秒跑几条 |
| 稳定性 | 很稳 | 脆（依赖网络、时序、渲染） |
| 能发现 | 逻辑分支、边界条件 | **CORS 配错、字段名对不上、Cookie 没带上、守卫拦了正常用户** |
| 发现不了 | 任何"连起来"的问题 | 边界条件（覆盖率太低，跑不起那么多） |

一句话：**单测告诉你"逻辑对不对"，E2E 告诉你"连起来能不能用"。**

本项目实测：54 个单测覆盖了分页计算、权限判定、Token 轮换、AI 结果清洗等
全部逻辑分支。但它们**跑在替身上**，而替身不会校验"你传给数据库的语句合不合法"。

这不是假设 —— 本项目真的踩到过：点赞与评论的计数器自增使用了**聚合管道**写法，
而从 Mongoose 9 起，传数组给 `findOneAndUpdate` 必须显式声明 `updatePipeline: true`，
否则直接抛 `MongooseError`。

结果是：**54 个单测全绿，而点赞和评论 100% 返回 500。**
只有 E2E 抓住了它（详见踩坑 6）。

### 2. E2E 不追求覆盖率

它只覆盖**关键路径** —— 能交付价值的那几条。
本项目就一条：**一个新用户能注册、发帖、互动。**

给 E2E 追求覆盖率的结果是：测试套件又慢又脆，
最后没人愿意跑它，于是它形同不存在。

### 3. 可重复性：E2E 的第一要求

```ts
const uniqueEmail = `e2e-${Date.now()}@example.com`
```

如果写死一个邮箱，**第二次跑就必然失败** —— 因为邮箱有唯一索引。
于是你的 E2E 只有第一次是绿的，之后就没人信它了。

> **不可重复的测试等于没有测试。**
> 它比"没有测试"更糟：它会消耗你的信任，让你开始忽略红色。

同理，用例之间如果有状态依赖（注册的账号被后面的用例复用），
就应该**串行执行**：

```ts
test.describe.configure({ mode: 'serial' })
workers: 1
```

能并行的才并行。有共享状态的测试串行跑更省心。

### 4. `test.step`：让失败告诉你"哪一步坏了"

```ts
await test.step('提交后跳转到详情页', async () => {
  ...
})
```

不用 `test.step` 时，失败信息是"第 42 行断言失败"，
你得回去读代码才知道发生了什么。

用了之后，报错里会直接写出"提交后跳转到详情页"这一步挂了 ——
**排查时间从"读代码"变成"读报错"**。

### 5. 上线前必须切换的配置

开发时的"方便"设置，上线时大多要反过来：

| 配置 | 本地开发 | 线上 | 不改的后果 |
| --- | --- | --- | --- |
| `CORS_ORIGIN` | `http://localhost:3001` | 前端真实域名 | 所有请求被浏览器拦下 |
| Atlas IP 白名单 | `0.0.0.0/0`（图方便） | 收紧为服务出口 IP | 数据库对全网暴露 |
| `COOKIE_SAME_SITE` | `lax`（同站可用） | **`none`**（跨域时） | 登录成功但一刷新就掉线，**且无报错** |
| `NODE_ENV` | 默认 `development` | `production` | `secure` Cookie 不生效 |
| 前端 API 地址 | `http://localhost:3000/api` | 后端真实域名 | 请求发到不存在的地方 |

**最后两行最容易翻车，因为它们的失败方式很隐蔽：**
Cookie 被静默丢弃、`secure` 标志没生效 —— 浏览器不会报错，只是行为不对。

### 6. 构建产物是什么

| 应用 | 产物 | 怎么跑 |
| --- | --- | --- |
| Nuxt 前端 | `.output/` | `node .output/server/index.mjs`（Node 服务端渲染） |
| NestJS 后端 | `dist/` | `node dist/main.js` |
| VitePress 电子书 | `.vitepress/dist/` | **纯静态**，任何静态服务器都行 |

一个细节：**前端产物里没有 `.env`**。
`NUXT_PUBLIC_*` 是在**构建时**注入的，所以改 API 地址需要重新构建；
而后端的 `MONGODB_URI` 是**运行时**读取的，改环境变量重启即可。

> 分不清"构建时"与"运行时"，是部署时最常见的困惑来源之一。

## 三、代码走读

### `playwright.config.ts`

三个刻意的设置，每个都对应一种"常见的错误做法"：

```ts
fullyParallel: false,   // 用例之间有真实状态依赖，并行会互相干扰
workers: 1,
retries: 0,             // 不用重试掩盖偶发失败 —— 要看真实的失败
trace: 'retain-on-failure',   // 失败时保留可回放的操作轨迹
```

`retries: 0` 特别值得说：很多人喜欢设 `retries: 2` 让 CI 变绿。
但那只是**把偶发失败藏起来**。偶发失败往往正是竞态、超时、
状态泄漏这类真实问题的信号 —— 而它们在线上会以更糟的形式出现。

### `e2e/studyplan.spec.ts`

用例的组织顺序就是**用户的真实旅程**：

```text
注册 → 发帖 → 点赞 → 评论（含删除）→ 标签筛选 → 未登录被拦
```

每一步都用 `test.step` 拆开。另外注意"未登录被拦"这一条：

```ts
const context = await browser.newContext()   // 全新上下文 = 从未登录过的浏览器
```

它验证的是一个**完整的安全边界**：前端守卫拦住了页面、
后端守卫拦住了接口。两者缺一，这条用例都不会过。

#### 会话共享：本文件最关键的一处设计

用例按"一个用户的旅程"组织，这要求所有用例**共用同一个浏览器上下文**。
但 Playwright 默认**为每个 test 新建上下文** —— 于是 Cookie 不共享，
而本项目的 Refresh Token 恰恰在 httpOnly Cookie 里。

修法是定义一个 worker 作用域的 fixture：

```ts
const test = base.extend<Record<string, never>, { session: Page }>({
  session: [
    async ({ browser }, use) => {
      const context = await browser.newContext()
      const page = await context.newPage()
      await use(page)          // 整个 worker 共用这一份
      await context.close()    // use() 之后是清理逻辑
    },
    { scope: 'worker' },
  ],
})
```

改完之后还有一份**额外收获**：「发帖」用例里的 `page.goto('/posts/new')`
变成了一次**真正的整页刷新** —— 内存里的 Access Token 会丢，
必须靠 Cookie 换新的才能留在页面上。

也就是说，这条路径**顺带验证了"刷新页面后仍保持登录"**。
这条需求单测和 mock 都覆盖不到，只有共享上下文的 E2E 能测。

## 四、踩坑记录

### 坑 1 · 构建工具清理旧产物时会撞上"批量删除保护"

现象：`nuxt build` 在最后一步失败，报错和编译毫无关系：

```text
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":503,"threshold":500,...}
```

原因：Nitro 在写入新产物前会先清空旧的 `.output` 目录。
而这个开发环境有一层"批量删除保护"，一次删除超过 500 个文件就被拦下。

**这不是代码问题，是环境约束** —— 但它揭示了一个通用事实：

> 构建工具会**主动清理上次的产物**，所以"产物目录里有别人放的东西"
> 是一件危险的事。反过来说，如果哪天你发现"改了代码但构建结果没变"，
> 第一个要怀疑的就是产物目录没被清干净。

解决办法是让产物目录保持干净（本次是手动清掉 `.output` 再构建）。

### 坑 2 · E2E 写死测试数据 → 第二次跑必挂

最初的写法是 `const email = 'e2e@example.com'`。

它第一次跑会绿，因为邮箱没被注册过。第二次跑就会红：
后端返回 409 `这个邮箱已经被注册了`。

**更糟的是这类失败的"信号质量"很低** —— 你看到的是"注册失败了"，
而真正的原因在测试数据的设计上，不在业务代码上。

改成带时间戳的邮箱之后，每次运行都是一个全新用户，用例可以无限重复执行。

### 坑 3 · 前端产物里没有 `.env`

部署时最容易犯的错：在后端平台上配好了环境变量，
然后去前端平台也配 `MONGODB_URI` —— 那是配错地方了。

更实际的困惑是：**在平台上加了 `NUXT_PUBLIC_API_BASE`，但它没生效**。

原因：`NUXT_PUBLIC_*` 是**构建时**注入的。平台通常只支持"部署时"设置变量，
所以要确认你的平台是在构建前注入变量，还是构建后。
如果它不支持构建时注入，就必须**改代码里 `nuxt.config.ts` 的默认值**。

> 一个通用的排查思路：**改一个环境变量，然后看它到了哪一步。**
> 如果改了没反应，就说明你改的那个环节根本没有读它。

### 坑 4 · `NODE_ENV=production` 会连带改变一堆行为

上线时设 `NODE_ENV=production` 是常识，但它的影响面比想象中大得多：

- NestJS 默认不再打印详细的启动日志；
- 本项目里 `secure` Cookie 标志**只有在 production 下才生效** ——
  本地测试时你会觉得"设了也没用"，其实是没进入那个分支；
- 很多库会切换错误处理策略（比如吞掉堆栈）。

所以：**上线后第一件事是把日志等级看一遍**，
否则你会以为"服务崩了但日志是空的"。

### 坑 5 · 上下文隔离会伪装成"登录态有 bug"（最有价值的一个）

现象：E2E 第一条「注册」通过，第二条「发帖」却跳回登录页。

第一反应必然是"应用的登录态有 bug"。但**应用是对的**：

```text
✓ 注册用例通过  → 全程客户端跳转，内存里的 Access Token 够用
✗ 发帖用例失败  → page.goto() 是整页刷新，内存 Token 丢失
                  → 需要靠 Cookie 换新 Token
                  → 但 Playwright 每个 test 都是新上下文，Cookie 根本不存在
```

**怎么确认是"没有 Cookie"而不是"代码错了"？** 看网络层，不看界面：

```text
POST /api/auth/refresh => 401 | cookie发送=False
                              ^^^^^^^^^^^^^^^^ 决定性证据
```

`Set-Cookie` 从没被带出去过，说明浏览器上下文里压根没有它。
如果代码有问题，你会看到"带了 Cookie 但返回 401"——
**两者的排查方向完全不同**。

这次调查用到的两件工具，值得记住：

1. **Playwright 的 trace**（`trace: 'retain-on-failure'`）里有完整网络记录，
   可以直接读出每个请求的方法、URL、状态码和请求头；
2. **服务端日志**要能回答"这个请求到底到没到我这"。
   如果日志里一条刷新记录都没有，就说明问题在更前面。

> 教训：**E2E 失败时，先判断"是应用错了还是测试没模拟对"。**
> 这一步判断错了，你会花几个小时去修一个并不存在的 bug。

### 坑 6 · 单测全绿，但功能是坏的：Mongoose 9 的 `updatePipeline`

现象：点赞和评论接口 **100% 返回 500**，而 54 个单测全部通过。

真实原因（从 stderr 日志拿到）：

```text
MongooseError: Cannot pass an array to query updates unless
the `updatePipeline` option is set.
    at PostsService.adjustCounter (posts.service.ts)
```

代码本身设计是对的 —— 用聚合管道 `$set + $max` 做原子自增，
既保证不丢更新（比"读-改-写"安全），又保证计数不会变成负数。
**只是 Mongoose 9 改了规则**：数组形式的更新必须显式开启：

```ts
{ returnDocument: 'after', updatePipeline: true }
```

**为什么单测抓不到？** 因为单测里 `postModel` 是替身。
替身只记录"你调用了 findOneAndUpdate、参数是这些"，
它**不会**去校验"这个更新语句符不符合 MongoDB 的语法"。
这个校验只有真实数据库驱动才会做。

> 这正是"单测与 E2E 互补"最好的例子：
> **mock 证明你的逻辑对，但证明不了你用的库调用方式对。**

顺带两件事：

- 同一次排查还发现 `new: true` 在 Mongoose 9 已弃用，应改为
  `returnDocument: 'after'`。**库的大版本升级常常就藏在这种地方** ——
  不报错，只警告，然后在下个版本突然变成错误。
- 「点赞」用例当时是**通过**的，尽管后端返回了 500。
  因为前端做了**乐观更新**：点击后界面立刻变数字，掩盖了接口失败。
  > 界面上的成功不等于服务器上的成功。**看测试是否通过，不如看服务端日志是否干净。**

### 坑 7 · 500 是"静默"的：日志分流到了 stderr

排查 500 时最令人困惑的一步：接口明明返回 500，
但主日志文件里**一句错误都没有**。

原因是 **NestJS 的 Logger 把 ERROR 级别写到 `stderr`**，
而我把标准输出和标准错误重定向到了两个不同的文件，
只看了前者。

```powershell
# 标准输出与标准错误是两条独立的流
Start-Process node -ArgumentList 'dist/main.js' `
  -RedirectStandardOutput 'api-run.log' `
  -RedirectStandardError  'api-err.log'    # ← 堆栈在这里
```

> **通用教训：排查服务端问题时，一定要同时看 stdout 和 stderr。**
> 「日志是空的」有两种可能：真的没报错，或者你正在看错误的那个文件。

这次顺手还把异常过滤器的日志策略改对了：
**统一按状态码分级，而不是按异常类型。**
早期实现只记录非 `HttpException`，结果"我们自己主动抛出的 500"
会变成完全静默的故障 —— 而这种故障最难查，因为它看起来像一切正常。

### 坑 8 · SSR 正常，但整页交互是死的

**这是本次最严重、也最难发现的一个。**

现象：页面该有的全都有 —— 标题、列表、卡片、数据，一切正常。
但**点任何按钮都没反应**：切换筛选、打开抽屉、点「问 AI」，全部静止。
不打开控制台，完全看不出它坏了。

真实原因：整页客户端 JS 根本没跑起来。

```text
SyntaxError: The requested module '.../packages/shared/dist/index.js'
  does not provide an export named 'avatarGradientClass'
```

共享包编译出来是 **CommonJS**（NestJS 必须跑 CJS），而浏览器只认 **ESM**。
Vite 默认**不预打包 workspace 链接包**，于是这个 CJS 文件被当成源码直接送进浏览器，
只能靠"静态导出识别"兜底 —— 新增一个导出之后识别没跟上，
模块加载抛错，**水合（hydration）整体失败**。

**为什么它比"普通的水合问题"更难查**：

| 你看到的 | 真相 |
| --- | --- |
| 页面完整、布局正常 | 那是 SSR 渲染出来的 HTML |
| 数据正确、卡片有内容 | 那是服务端取的，与客户端无关 |
| 不点按钮看不出异常 | 只有控制台里躺着那一行 SyntaxError |
| 单测、接口测试全绿 | 接口本来就没问题 |

修法是让 Vite 强制预打包共享包，交给 esbuild 做完整的 CJS → ESM 转换：

```ts
// apps/web/nuxt.config.ts
vite: {
  optimizeDeps: { include: ['@studyplan/shared'] },
}
```

> **SSR 应用有一个特殊的盲区：服务端渲染的 HTML 会掩盖客户端的失败。**
> "页面能看"和"页面能用"是两件独立的事，而前者会把后者的问题藏得严严实实。
>
> 所以"页面打得开"**不是**一条合格的验收标准。
> 合格的验收标准是：**在真实浏览器里点一遍，看到它真的响应了。**

> 再补一条排查经验：这次的第一反应是"Vite 缓存过期"，
> 但重启 dev server 之后**问题依旧** —— 缓存只是表象，模块格式才是根因。
> 当一个解释"能说通现象"、但照着改完却没用时，它多半不是真因。

## 六、术语表

| 术语 | 一句话解释 |
| --- | --- |
| E2E 测试 | 用真实浏览器跑真实系统的端到端测试 |
| 关键路径 | 能交付核心价值的那几条操作流程 |
| 可重复性 | 同一个测试可以反复执行且结果一致 |
| trace | Playwright 记录的操作轨迹，可回放排查 |
| 构建时注入 | 变量在构建阶段被写进产物，改了要重新构建 |
| 运行时读取 | 变量在进程启动时读取，改了重启即可 |
| 环境差异 | 本地与线上在配置、版本、网络上的不同 |
| 回退 | 部署失败时恢复到上一个可用版本 |


但比这些技术点更重要的是**三样习惯**，它们才是这本书真正的产出：

1. **先想清楚"失败了会怎样"，再动手写。**
   （AI 走旁路、网络故障与 404 分开、幂等接口 —— 全是这个习惯的产物）
2. **把正确性交给有约束能力的那一层。**
   （唯一索引、`$inc`、`Schema` —— 都优于应用层的"检查一下"）
3. **把"看起来对了"变成"验证过它是对的"。**
   （本项目的 `jti` 缺陷、静默失效的头像配色、以及那个
   "单测全绿但点赞评论全 500" 的 `updatePipeline` 问题，
   都是靠断言、产物检查和 E2E 抓出来的 —— 没有一个是"看代码看出来的"）

代码会过时，框架会换代 —— 这三条不会。
