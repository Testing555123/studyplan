## 二、核心概念

### 1. 评论为什么必须是独立集合

内嵌写法看起来更自然：

```js
{ title: '...', comments: [ {...}, {...} ] }
```

但它有一个硬性天花板：**MongoDB 单个文档最大 16MB**。
一条热门帖子的评论迟早会把这个空间撑爆 —— 而那天到来时，
表现是"这篇帖子的评论突然发不出去了"，且不会有任何预警。

独立集合没有这个上限，还带来额外好处：评论可以独立分页、独立删除，
写入时也不会锁定整个帖子文档。

代价是每次要按 `postId` 再查一次 —— 所以**必须有 `postId` 索引**。
没有索引的代价不是"慢一点"，而是"每条评论都要扫全集合"。

### 2. 点赞为什么要用独立集合 + 复合唯一索引

直觉写法是在帖子上存一个数组：

```js
{ _id: postId, likedBy: ['u1', 'u2', ...] }
```

两个致命问题：

1. **数组无限增长**，最终撞上 16MB 上限；
2. **高并发下写冲突**：每次点赞都改同一个文档，MongoDB 对单文档的写入是串行的。

独立集合把"一条点赞"变成一行记录，两个问题同时消失。而那"一个人不能重复点赞"
靠什么保证？靠**复合唯一索引**：

```ts
LikeSchema.index({ postId: 1, userId: 1 }, { unique: true })
```

> **这个索引不是性能优化，它是业务规则的执行者。**

### 3. 正确性交给有约束能力的那一层

有了上面的唯一索引，服务层就**不需要**"先查有没有赞过"：

```ts
// ❌ 有并发漏洞：两个人可能同时查到"没赞过"，然后都去插入
const exists = await likeModel.findOne({ postId, userId })
if (exists) throw new ConflictException()

// ✅ 直接插，让数据库裁决
try {
  await likeModel.create({ postId, userId })
} catch (error) {
  if (isDuplicateKeyError(error)) { /* 已经赞过了 */ }
}
```

"查"和"插"之间有一个时间窗口。应用层的检查只能用来
"给出更友好的提示"，**不能用来保证正确性**。

> 一条通用原则：**正确性交给有约束能力的那一层去做。**
> 并发场景下，能提供约束的只有数据库。

### 4. `$inc` 与 `$max`：解决"读改写"竞态

```ts
// ❌ 读 → 改 → 写：两个人同时读到 10，都写回 11，两次点赞只涨了 1
post.likeCount = post.likeCount + 1
await post.save()
```

```ts
// ✅ 让数据库做加法，中间不给别人插队的机会
{ $inc: { likeCount: 1 } }
```

但 `$inc: -1` 有个副作用：计数已经是 0 时会变成 **-1**。
一个"-1 个赞"的界面比少一个赞难看得多，而且它会一直留在数据库里。

所以本项目用的是**聚合管道更新**，在数据库里同时完成加法和兜底：

```ts
[ { $set: { likeCount: { $max: [0, { $add: ['$likeCount', delta] }] } } } ]
```

一句话：**`$inc` 保证不丢更新，`$max` 保证不出负数。**

### 5. 幂等：为什么点赞不用 toggle

假设接口设计成 `POST /like` 做**切换**：

- 用户手抖点两次 → 点赞又被取消了；
- 网络超时后客户端重试一次 → 同样把刚点的赞取消了。

而 `PUT /like`（点赞）和 `DELETE /like`（取消）是**幂等**的：
调用一次和调用十次结果完全一样，重试是安全的。

> 判断标准：**这个操作重复执行一次，结果会变吗？**
> 会变 → 不该用可重试的语义表达它。

前端因此需要知道"我想达成什么状态"，而不是"切换一下"。
这反而让交互逻辑更清晰 —— 乐观更新时它本来就是知道目标状态的。

### 6. 复合索引的前缀复用

`{ postId: 1, userId: 1 }` 因为 `postId` 是**前导字段**，
所以它同时能服务"查某帖的所有点赞"这类只用 `postId` 的查询。
因此**不需要**再单独建一个 `{ postId: 1 }` 索引 —— 那是纯浪费。

规则：`{ a: 1, b: 1 }` 能服务 `a` 和 `a + b`，但服务不了单独的 `b`。

## 三、代码走读

### `likes.service.ts` —— 幂等是怎么写出来的

`like()` 里没有"先查有没有赞过"，而是直接插入并捕获唯一索引冲突：

```ts
try {
  await this.likeModel.create({ postId, userId })
} catch (error) {
  if (!isDuplicateKeyError(error)) throw error
  // 冲突 = 已经赞过 = 目标状态已达成 → 返回成功，且**不重复计数**
  const counters = await this.postsService.getCounters(postId)
  return { liked: true, likeCount: counters?.likeCount ?? 0 }
}
```

注意冲突分支里**绝不能**再 `$inc` —— 否则快速连点就会把计数点出天际。

`unlike()` 同理：`deleteCount === 0` 说明本来就没赞过，
那也不该减计数（否则会把计数减成负数）。

### `posts.service.ts` —— `adjustCounter` 的管道更新

```ts
{ $set: { [field]: { $max: [0, { $add: [`$${field}`, delta] }] } } }
```

注意它是被**别的模块**调用的 —— 这正是 `PostsModule` 里
`exports: [PostsService]` 的用途。点赞模块不直接碰 `posts` 集合，
而是通过帖子模块暴露的语义明确的接口来改数据，
这样"帖子文档长什么样"依然只有帖子模块知道。

### 跨模块协作的依赖链

```text
CommentsModule ──imports──▶ PostsModule ──exports──▶ PostsService
LikesModule    ──imports──▶ PostsModule
```

如果 `PostsModule` 忘了写 `exports`，两个模块会**同时**在启动时报
`Nest can't resolve dependencies of the CommentsService (..., ?)`。
那个 `?` 就是在说"这个位置我找不到可注入的东西"。

> 删除"看起来没被用到"的 `exports` 时，一定要先想清楚
> 有没有别的模块在依赖它。

### 一个诚实的说明：三步操作不是原子的

`CommentsService.create()` 做了三件事：

1. 校验帖子存在；
2. 写入评论；
3. 原子增加帖子的评论计数。

**这三步不是原子的。** 如果第 3 步失败，评论已经写进去了，
但计数没涨 —— 数据会不一致。

彻底解决需要数据库事务（MongoDB 副本集支持，Atlas M0 也支持）。
本项目没用事务，理由是：

- 计数是**展示用的派生数据**，偶发偏差不影响业务正确性；
- 引入事务会给这个教学项目增加一层不必要的心智负担。

**但你要知道这个缺口在哪，以及生产环境下该怎么补。**

### 重构时机：第二个使用者出现时

阶段 3 时"内嵌作者快照"只属于帖子，写在 `post.schema.ts` 里就够了。
阶段 6 加评论时，"评论也要显示作者名"是同一个需求 ——
于是把它提到了 `common/schemas/author.schema.ts`。

同一阶段还提取了 `common/utils/mongo-errors.ts`（第二个用它的地方是点赞）。

> 判断该不该抽取的信号：**第二个使用者出现的时候。**
> 只有一个使用者时提前抽，只是把代码拆到两个文件里，反而更难读。

## 四、踩坑记录

### 坑 1 · `$inc: -1` 会把计数减成负数

取消点赞时如果直接 `$inc: { likeCount: -1 }`，而计数恰好是 0，
它就会变成 -1 —— 而且**永远留在数据库里**，界面上显示"-1"个赞。

修复是用聚合管道里的 `$max: [0, ...]` 在数据库层兜底。
这不是"多加一层保险"，而是**正确性的必要条件**：
应用层的判断在并发下不可靠，兜底只能放在能提供约束的那一层。

### 坑 2 · toggle 语义在重试下会翻转

最初打算用 `POST /like` 一个接口做切换，代码更少。
但很快意识到一个问题：**我们自己实现的 401 静默续期会重放请求**。

- 请求因为 Access Token 过期被拒（401）→ 刷新令牌 → 重放原请求；
- 这一次 401 时业务逻辑**还没执行**，所以重放是安全的 ✓。

但其它重放场景（网络超时重发、用户连点、将来可能加的重试中间件）
就没有这个保证了。对一个 toggle 接口，重放等于"撤销"。

改成 `PUT` / `DELETE` 之后，重放在语义上就是安全的。

> **一个接口设计上的问题，往往来自"调用方可能做什么"，而不是"它自己要做什么"。**

### 坑 3 · 复合索引前缀复用，不需要重复建索引

一开始给 `likes` 建了两个索引：
`{ postId: 1, userId: 1 }`（唯一）和 `{ postId: 1 }`。

第二个是多余的 —— 复合索引以 `postId` 为前导，本来就能服务只用 `postId` 的查询。
多余的索引会**占空间、拖慢写入**，而收益为零。

> 新手最常见的索引错误不是"没建索引"，而是"给每个字段都建了索引"。

### 坑 4 · ObjectId 不转字符串，前端会读到序列化包装

`_id` 和 `postId` 在数据库里是 ObjectId 对象。
如果 mapper 里直接返回 `doc._id`，经过 JSON 序列化后
前端拿到的可能是 `{}` 或 `{"$oid": "..."}` 这类包装，
表现就是"字段看着有，读出来是空的"。

所以 mapper 里对它们都显式做了 `String()` 转换。
**映射层的职责之一就是抹平存储类型与传输类型之间的差异。**

### 坑 5 · 幂等接口返回成功而不是 409

"已经赞过了"这种情况，最初想返回 `409 Conflict`。
但它其实是一个**成功的幂等结果** —— 用户想要的状态（已点赞）已经达成了。

返回 200 让客户端逻辑简单得多：不需要处理"这次算成功还是失败"，
乐观更新也不会被一个错误打断。

> 幂等接口的失败语义要谨慎设计：**"目标状态已达成"不是错误。**

## 六、术语表

| 术语 | 一句话解释 |
| --- | --- |
| 16MB 上限 | MongoDB 单个文档的硬上限，内嵌数组容易撞上 |
| 复合唯一索引 | 多个字段组成的唯一约束，可同时充当业务规则执行者 |
| 索引前缀 | 复合索引的前几个字段可被单独使用，复用同一个索引 |
| 原子更新 | 由数据库保证不可分割的更新，如 `$inc` |
| 聚合管道更新 | 用 `[ { $set: ... } ]` 形式在数据库内完成计算 |
| 幂等 | 重复执行结果不变，因而重试是安全的 |
| 读改写竞态 | "读 → 算 → 写"三步之间的窗口导致丢失更新 |
| 派生数据 | 可由其它数据算出的展示字段，如计数 |
| 降级 | 次要功能失败时不让主要功能受影响 |
| TOCTOU | 检查时与使用时不一致，导致权限绕过 |
