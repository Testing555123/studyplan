# 调试经验：出问题时先看什么

> 这一页解决一个很具体的问题：**问题出现时，按什么顺序找原因，才能最快定位。**
>
> [上一篇](./deployment-lessons) 讲"坑长什么样"，这一篇讲"怎么找坑"。所有例子都是真实发生过的——包括一个**至今没查明根因**的问题，我也把它写进来了。

---

## 一、定位顺序：从最接近现场的证据开始

出问题时的默认反应是"看代码猜原因"。这个顺序几乎总是最慢的。按下面这个顺序，通常能在几步内收敛：

| 顺序 | 证据 | 在哪拿 | 它能直接回答什么 |
| --- | --- | --- | --- |
| 1 | **平台运行日志**（容器 stdout/stderr） | 平台的 logs 命令/面板 | 进程到底起来没有、报了什么错 |
| 2 | **入口与子进程日志** | 自己写的入口脚本打的日志 | 是"没起来"还是"起来了但某个依赖不对" |
| 3 | **请求级日志**（带 requestId） | 后端的访问日志中间件 | 请求到没到、状态码、耗时 |
| 4 | **页面状态**（DOM 快照 / 截图） | Playwright 失败时自动留存 | 用户实际看到了什么（而不是你以为的） |
| 5 | **网络层**（DNS / TCP / TLS） | `curl -v`、`--resolve`、端口探测 | 是"连不上"还是"连上了但被拒" |
| 6 | 代码推测 | — | 前五步都干净之后才轮到它 |

**为什么把代码放最后**：代码是"你认为会发生什么"，日志与页面是"实际发生了什么"。两者冲突时，输的永远是代码。

> 一个直接的例子：本次"容器起来了却 502"的问题，日志里平台的报错是"启动超时"，
> 看着像端口配错；而真正的根因（环境变量校验失败）藏在**子进程日志**里。
> 如果先按"端口问题"去改代码，会白改好几轮。

## 二、只在线上复现的问题，怎么定位

**先说为什么它难**：本地是"进程一直活着"，线上是"实例随时生灭"。凡是依赖"进程活着"的行为（内存缓存、内存计数、启动时初始化、常驻连接），到了线上语义就变了。

**再说为什么它一定会被误判**：这类问题通常**不会稳定复现**（冷启动窗口只有几秒、缩容只在无流量后发生），于是你会下意识怀疑"是不是代码有随机 bug"。

**定位方法：把观测能力当成要主动设计的东西，而不是出事后再加。**

本次实际做的三件事：

| 手段 | 作用 | 实现位置 |
| --- | --- | --- |
| 统一访问日志 + requestId | 把"一次请求"在多个进程间串起来 | `apps/api/src/common/middleware/http-logger.middleware.ts` |
| requestId 写进响应头 | 用户报错时能拿到 id，直接定位那一条日志 | `apps/api/src/common/interceptors/request-id.interceptor.ts` |
| 入口脚本打子进程生命周期日志 | 区分"没起来"与"起来了但依赖不对" | `docker/vercel/entrypoint.mjs` |

**一个具体收获**：把入口脚本从"等子进程就绪再监听"改成"先监听"之后，同一个故障场景下的日志**直接给出了根因**。改动本身只是调换了两行代码的顺序，但它把"平台唯一的观测窗口"保住了。

> 观测能力的价值是**复利**的：它在你最需要的那一刻之前就已经存在。

## 三、端到端测试：唯一能覆盖真实链路的证据

单元测试用替身把数据库和网络都换掉了，所以它证明的是"逻辑对"；**端到端测试开真实浏览器、点真实按钮、发真实请求**，它证明的是"连起来能用"。

**为什么它值得对着线上跑**：同一套用例打在线上，会覆盖本地根本不存在的东西。

本次它抓到两个**本地永远复现不出来**的问题：

| 问题 | 为什么本地抓不到 |
| --- | --- |
| 冷启动窗口内整页 502 | 本地进程一直活着，没有冷启动这回事 |
| 首次点击被水合窗口吞掉 | 本地水合快，窗口小到几乎撞不上 |

**跑的时候要注意**：

```bash
# 指向线上环境（同一套用例，只换基地址）
E2E_BASE_URL=https://你的域名 pnpm --filter @studyplan/web e2e
```

- **它会往目标库写真实数据**（真注册、真发帖）。所以**跑之前先给数据库留基线**，否则脏数据只能靠直接连库清理。
- 访问境外站点可能需要代理，配置里已支持：

```powershell
$env:E2E_BASE_URL='https://你的域名'
$env:E2E_PROXY='http://127.0.0.1:7897'   # 可选，按需
pnpm --filter @studyplan/web e2e
```

> **本地通过 ≠ 线上通过。** 只有两边都跑过，才谈得上"部署成功"。

## 四、SSR 水合竞态：前端 E2E 最经典的陷阱

**现象**

点击一个按钮，**不报错，也不生效**。DOM 里那个按钮明明在，Playwright 也说"点击成功"，但视图没有任何变化。几步之后的断言超时，失败位置离真正的成因很远。

**为什么**

服务端渲染的 HTML 一到浏览器，**DOM 就已经存在**了；但 Vue 的事件处理器要等**水合（hydration）**完成才挂上。这中间有一个窗口，落在这个窗口里的点击会被静默吞掉。

线上（冷启动 + 跨网络）会把这个窗口放大，所以线上比本地更容易踩到。

**怎么修（两种，别用错）**

**① 幂等交互用重试**：点完必须观察到状态变化，否则再点一次。

```ts
await expect(async () => {
  await page.getByRole('button', { name: '注册' }).first().click()
  await expect(page.getByRole('heading', { name: '创建你的账号' })).toBeVisible({ timeout: 1000 })
}).toPass({ timeout: 15_000 })
```

**② 开关型元素（点一次选中、再点取消）不能简单重试**——重试会把已选中的取消掉，失败会从"没选上"变成"选上又取消"，更难查。要**先看状态再决定点不点**：

```ts
const selectedCount = page.getByText(/已选\s*1\s*\/\s*5/)

await expect(async () => {
  if (!(await selectedCount.isVisible())) {
    await page.getByRole('button', { name: 'Nuxt', exact: true }).click()
  }
  await expect(selectedCount).toBeVisible({ timeout: 1000 })
}).toPass({ timeout: 15_000 })
```

**如何预防**

把"**点完必须观察到状态变化**"当成写交互用例的规范。只写"点击"不写"验证点击的效果"，就是把水合竞态留给未来的自己。

## 五、失败位置离成因很远时，该看什么

**案例**：发帖用例失败在

```text
TimeoutError: page.waitForURL: Timeout 20000ms exceeded.
> await page.waitForURL(/\/posts\/[a-f0-9]{24}$/, { timeout: 20_000 })
```

看着像"路由跳转有问题"。实际根因是：**标签一个都没选中 → 前端按设计拦住了提交 → 根本没发出那个请求。**

**怎么发现的**（三个证据，缺一不可）：

| 证据 | 看到了什么 |
| --- | --- |
| Playwright 自动留存的 `error-context.md` 页面快照 | `已选 0 / 5`——标签没选上，一眼看出 |
| 失败截图 | 表单内容都在、实时预览也正常，说明水合是好的、应用没坏 |
| **后端日志** | 连 `POST /api/posts` 这条记录都没有 → 请求从未发出 |

**可复用的判断顺序**：

```text
1. 请求发出去了吗？
     ├─ 没发出 → 前端（校验、守卫、水合、状态）问题
     └─ 发出了 → 2. 后端收到了吗？
                   ├─ 没收到 → 网络/网关/代理问题
                   └─ 收到了 → 3. 后端返回了什么？（看状态码与错误体）
```

**先回答"有没有发生"，再回答"为什么失败"。** 这两步的顺序反了，就会在错误的地方找原因。

## 六、网络问题的三段式排查

"打不开"是一句没有信息量的话。把它拆成三段，每段都有明确的工具和判据：

```text
① DNS 解析  →  域名解析到哪个 IP？（可能被污染/劫持）
② TCP 连接  →  能连上那个 IP 的 443 吗？（可能被阻断）
③ TLS 握手  →  握手完成了吗？（可能按域名特征被重置）
```

| 工具 | 用途 |
| --- | --- |
| `Resolve-DnsName` / `nslookup` | 看解析结果。**同一域名多次解析结果不一致 = 被污染** |
| `Test-NetConnection -Port 443` | 只看 TCP 层是否通 |
| `curl --resolve 域名:443:IP` | 绕过 DNS，自己指定 IP，把变量隔离出来 |
| `curl -v` | 看断在哪一步（Trying / Connected / TLS / 收到响应） |

**本次实测的完整结论**（这就是这套方法的价值）：

```text
studyplan-teal.vercel.app  → 解析到 31.13.92.5（Meta 段）、205.251.x（AWS 段），每次不同   ← ① DNS 被污染

直连 Vercel 边缘 IP（--resolve，SNI 用 vercel.com）：
  76.76.21.21 / 76.76.21.98 / 216.198.79.1  → 全部 200，连接耗时 0.03-0.10s            ← ② TCP 是通的

同一 IP，换成 SNI=studyplan-teal.vercel.app：
  Recv failure: Connection was reset
  schannel: failed to receive handshake, SSL/TLS connection failed                      ← ③ 断在 TLS 握手
```

**结论**：被拦的是 `*.vercel.app` 这个**域名模式**，不是平台的 IP。

这个结论直接改变了决策——如果当时停在"打不开 = 平台不可用"，就会白白放弃一条可行路径。**自有域名绑上去之后，很可能就能直连。**

> 遇到"某站点打不开"，先问自己：**是域名的问题，还是 IP 的问题？** 这两个的解法完全不同。

## 七、浏览器能打开、命令行不能打开：先查代理

**现象**：浏览器访问某个境外站点正常，但 `curl` 和 `node` 全部超时。

**为什么**：浏览器普遍自带安全 DNS（DoH），能绕过被污染的系统 DNS；而命令行走的是系统解析。所以"浏览器能开"**不代表**"网络通畅"。

**顺便记住一个反直觉点**：

```powershell
netsh winhttp show proxy
# Current WinHTTP proxy settings: Direct access (no proxy server).
```

这条命令显示"没有代理"**不等于真的没有代理**——它只管系统服务（WinHTTP），不管用户态程序（浏览器、curl、node 走的都是另一套）。用户态代理在注册表里：

```powershell
Get-ItemProperty 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings' |
  Select-Object ProxyEnable, ProxyServer
```

**一个快速的可用性判据**：扫一下常见代理端口有没有在监听。

```powershell
foreach ($p in 7890, 7897, 10809, 1080, 8080) {
  if (Get-NetTCPConnection -LocalPort $p -State Listen -ErrorAction SilentlyContinue) { "端口 $p 在监听" }
}
```

**本次实际情况**：`7897` 在监听（Clash 的默认混合端口）。确认之后，所有线上验证都通过它完成：

```powershell
curl -x http://127.0.0.1:7897 https://studyplan-teal.vercel.app/api/health
# {"status":"ok","info":{"mongodb":{"status":"up"}},...}   耗时 1.25s
```

> 排查"网络不通"之前，先确认**你是不是根本没在走你以为的那条网络**。

## 八、测试失败时，先分辨"环境问题"还是"用例问题"

**这一步能省下大量时间。** 方法是：**用同一套用例打两个环境，对比失败点。**

本次的真实数据：

| 环境 | 结果 |
| --- | --- |
| 线上（真实域名 + HTTPS） | **6 passed**（注册含整页刷新 → 发帖 → 点赞 → 评论 → 标签筛选 → 未登录拦截） |
| 本地（localhost） | 稳定失败在更早的一步 |

**这个对比直接改变了方向**：如果只看本地，结论会是"应用坏了、部署有问题"；两边一比才知道——**线上是好的，坏的是本地开发环境**。

> 同一套测试跑两个环境，不只是"顺便验证线上"，它还是**定位问题时最省事的二分法**。

## 九、一条如实挂账的未解问题

按前面所有方法排查过，但**根因仍未查明**的一件事，如实记在这里。

**现象**

本地开发模式下，端到端测试稳定卡在"点击页签后视图不切换"——**点击完全没有效果**，重试 15 秒都不行。而同一次运行里，服务端渲染的输出完全正常（用 curl 能拿到完整 HTML，且含有真实数据）。

**已排除**

| 假设 | 排除方式 | 结果 |
| --- | --- | --- |
| Nuxt 开发缓存陈旧 | 清掉 `.nuxt` 后重启、重跑 | 仍然失败 |
| 开发服务器启动方式不对 | 换成在包目录内直接启动 | 仍然失败 |
| 应用代码有问题 | 同一份代码在线上 6/6 通过 | 排除 |

**现有线索**（供后来者接手）

- 页面里客户端脚本的引用出现了 **Windows 绝对路径形态**：`/_nuxt/D:/.../entry.async.js`（而正常形态应是 `/_nuxt/@vite/client` 这类 URL）。但该 URL 单独请求能返回 `text/javascript`，所以**不能直接断定它是根因**。
- 开发服务器日志里有字体 provider 初始化失败（`fonts.google.com` 连接超时）与若干 Vue 警告。

**为什么把它写进文档**

因为"**结论未成立**"本身就是一个需要被传递的信息：

> 线上 `6 passed` 是真实通过的；但"**同一套测试本地与线上都绿**"这个更强的结论，**目前还不成立**。
> 把没解决的事标出来，比假装它不存在更安全——否则下一个人会以为"本地 E2E 本来就跑不过"，然后不再相信这套测试。

## 十、可复用的排查动作清单

按顺序做，不要跳。

**第一步：拿到现场证据**

- [ ] 平台运行日志（容器 stdout/stderr）看过了吗？
- [ ] 自己入口/子进程打的日志看过了吗？
- [ ] 有没有带 requestId 的请求级日志可以串起来？

**第二步：判断"有没有发生"**

- [ ] 请求发出去了吗（前端网络面板 / 后端有没有这条记录）？
- [ ] 后端收到了吗？返回了什么状态码？
- [ ] 页面**实际**长什么样（DOM 快照 / 截图），而不是你以为的样子？

**第三步：隔离变量**

- [ ] 换一个环境跑同一套测试，失败点变了吗？
- [ ] 网络问题：拆成 DNS / TCP / TLS 三段分别验证
- [ ] 只在某个环境复现：列出两个环境**所有**不同点（进程生灭、代理、缓存、构建期常量）

**第四步：改之前先写下假设**

- [ ] 我这次改动**预期**让哪条日志/哪个状态发生变化？
- [ ] 如果没变化，说明假设错了——不要继续在同一个方向上改

**贯穿全程**

- [ ] 有没有"我以为是错的、其实是对的"的部分（例如前端拦截提交是**设计如此**）？
- [ ] 未解决的问题有没有如实记下来？

---

## 十一、三句话

1. **先拿证据，再改代码。** 日志与页面说"实际发生了什么"，代码只说明"你以为会发生什么"。
2. **先问"有没有发生"，再问"为什么失败"。** 顺序反了，就会在错误的地方找原因。
3. **隔离变量是唯一的通用方法。** 换环境、分段测、绕开 DNS——本质都是"一次只改一个变量"。
