# 规划练习 7 · 拆解「阶段 8 · 测试与上线」

## 这一阶段的特殊性

前面七个阶段，你的运行环境只有一个：**你自己的电脑**。
而这一阶段要面对的是一个全新类型的问题：

> **"在我机器上是好的。"**

线上没有你的 `.env`、没有你的 Node 版本、没有你加过白名单的 IP、
也没有你那条能跑通一切的命令。

> 规划这类任务的诀窍是：**把所有"隐式依赖"变成"显式清单"。**

---

## 第一步：列出"我的机器上有什么，线上可能没有"

不要写部署步骤，先做**依赖盘点**。

```text
我的清单：
1.
2.
3.
4.
5.
```

<details>
<summary>提示</summary>

从"我第一次打开这个项目时做过哪些事"倒推。

那些你**做过一次就忘了**的事，正是线上会缺的东西：

```text
.env 文件          ← 需要手动创建并填写
Atlas IP 白名单    ← 需要加线上服务器的出口 IP
Node 版本          ← 线上可能是 18，而你本地是 24
pnpm 版本          ← 影响锁文件解析
端口约定           ← 线上通常由平台指定，不能写死
前端指向的 API 地址 ← 本地是 localhost，线上必须是真实域名
Cookie 的 SameSite ← 前后端不同域时必须改成 none
```

**这份清单就是这个阶段的主要工作量。** 部署本身往往只是几分钟的事。

</details>

## 第二步：排三步，并明确"每一步失败时怎么回退"

```text
第 1 步（失败时回退方式：              ）
第 2 步（失败时回退方式：              ）
第 3 步（失败时回退方式：              ）
```

<details>
<summary>提示</summary>

部署和前面的阶段有一个本质区别：**它在操作"真实存在的东西"**。

- 前三阶段写错代码，改回来就行；
- 部署时如果改了生产数据库的连接串、删了线上的环境变量，
  影响的就是真实可访问的服务。

所以要提前想好：**这一步搞砸了，我怎么回到上一步？**

对于本项目的规模，"回退方式"通常很简单（重新部署上一个版本、
把变量改回去）。但**"想过"和"没想过"在出事那一刻差别巨大**。

</details>

## 第三步：估工时，并把"环境差异排查"单独列出来

```text
第 1 步：____ 小时
第 2 步：____ 小时
第 3 步：____ 小时
其中"排查环境差异"占：____ 小时
```

<details>
<summary>提示</summary>

"环境差异排查"的时间几乎无法预估，因为它取决于**你第一份清单漏了多少**。

一个实用的估法：**清单里有几项，就按每项 15-30 分钟算**。
漏掉的项目会在你完全没预料到的地方冒出来，而且往往表现为
一个和根因看起来毫无关系的报错。

</details>

## 第四步：说出一个"上线前必须关掉的东西"

```text
我要关掉：____________________
不关的后果：__________________
```

<details>
<summary>提示</summary>

从"这些设置是为了方便开发"这个角度去找。

本项目里至少有两个：

- `CORS_ORIGIN` 里的本地地址 —— 线上不存在 `localhost:3001`，
  前端请求会被浏览器拦下；
- Atlas 的 `0.0.0.0/0` 白名单 —— 开发时图方便放开了所有 IP，
  线上如果不收紧，等于把数据库暴露给整个互联网。

**"开发方便"和"生产安全"经常是相反的，而部署就是把前者切换成后者的时刻。**

</details>

## 参考拆解（写完再看）

<details>
<summary>点开对照</summary>

### 隐式依赖清单

| 依赖 | 本地怎么来的 | 线上要做什么 |
| --- | --- | --- |
| `apps/api/.env` | 手动从模板复制并填写 | 在平台的"环境变量"面板逐项添加 |
| Atlas IP 白名单 | 加了`0.0.0.0/0`方便开发 | 收紧为线上服务出口 IP |
| Node 版本 | 本机 24.18.1 | 平台选 ≥20.19（NestJS 11 要求），或用 `engines` 声明 |
| pnpm | 本机 11.20.0 | 平台可能默认用 npm，需要显式指定 |
| 数据库连接串 | `mongodb+srv://...` | 同上，**绝不要写进代码** |
| 前端 API 地址 | `http://localhost:3000/api` | 改成后端线上域名（用 `NUXT_PUBLIC_API_BASE`） |
| CORS 白名单 | `http://localhost:3001` | 改成前端线上域名 |
| Cookie SameSite | `lax`（同站可用） | **必须改 `none`**，且后端要 HTTPS |
| `NODE_ENV` | 默认 development | 设为 `production`（否则 `secure` Cookie 不生效） |

**最后两条是本项目最容易翻车的**：前后端部署在不同域名下时，
`SameSite=lax` 会让浏览器直接丢掉 Refresh Cookie ——
表现是"登录成功了，但一刷新就变回未登录"，而且**没有任何报错**。

### 三步拆解

| 步骤 | 内容 | 失败时怎么回退 |
| --- | --- | --- |
| 第 1 步 | 补端到端测试（Playwright）：注册 → 登录 → 发帖 → 评论 → 点赞 → 标签筛选 | 测试代码不影响线上，直接删掉即可 |
| 第 2 步 | 后端先上线（它必须先可用），验证 `/api/health` 与 Swagger | 平台可以一键回滚到上一个部署 |
| 第 3 步 | 前端与电子书上线，改 `NUXT_PUBLIC_API_BASE` 与 `CORS_ORIGIN`，验证一次完整发帖 | 把环境变量改回旧值并重新部署 |

**为什么后端要先上？** 因为前端的所有页面都依赖它。
反过来先上前端，你会对着一个所有请求都失败的站点排查前端问题 ——
那是在错误的地方找原因。

### 顺序依据

- **E2E 放在最前面**：它是**上线前的最后一道自动检查**。
  先写它，后面每次改了配置重新部署，都能一键验证"整套流程还是通的"。
  如果放到最后，它就变成了"上线之后才补的作业"。
- **电子书最后上**：它是纯静态站点，没有任何依赖，
  随时可以上、失败也无所谓。把它排在关键路径之外。

### 工时估算参考

| 步骤 | 估时 | 依据 |
| --- | --- | --- |
| 第 1 步 | 4-8 h | Playwright 首次配置（浏览器下载、配置 baseURL、处理登录态复用）占一半时间 |
| 第 2 步 | 1-3 h | 后端平台选择 + 环境变量逐项填写 + 数据库白名单放行 |
| 第 3 步 | 1-3 h | 前端平台 + 环境变量 + CORS/Cookie 调试 |
| 其中排查环境差异 | **2-5 h** | 主要花在 CORS、Cookie、API 地址这三处 |
| **合计** | **8-19 h** | 约 2-4 天（比想象中长，主要因为"环境差异"） |

### 该砍的

> **自定义域名、HTTPS 证书、CDN、监控告警。**
>
> 它们都是真实生产环境必须有的东西，但**不是这个学习目标必须有的东西**。
> 这一阶段的目的是"让整套流程在一个真实可访问的环境里跑通"，
> 而不是"搭建一个生产级基础设施"。
>
> 明确记下来：这是有意识的取舍。等你真的要运营一个产品时，
> 它们会排在清单最前面。

### 一个容易被漏掉的规划项

**把 `README.md` 里的"快速开始"按线上流程重写一遍。**

这不是文档洁癖，而是一次**真实验证**：

> 如果你照着 README 从零开始能不能跑起来？
> 需要手动补充的步骤，说明 README 漏了。

几乎所有项目的 README 都在"作者自己的机器"这个隐含前提下写的 ——
而线上环境没有那个前提。**用别人的视角读一遍自己的文档，
是最便宜的可用性测试。**

</details>
