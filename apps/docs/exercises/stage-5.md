## 这一阶段的特殊性

评论、点赞、标签筛选看起来是三个独立的"小功能"，
代码量也不大。但它们第一次把你带到一个新领域：**并发**。

前面所有功能都是"读"或者"我改我自己的数据"，
天然不会冲突。而点赞是**很多人同时改同一条数据**。

> 规划这类任务的难点不在"要写什么"，
> 而在**识别出哪个地方会出现竞态**。

---

## 第一步：先找出"哪些操作会被并发执行"

不要写功能点，先做一次**并发风险扫描**。

```text
我的清单：
1.
2.
3.
```

<details>
<summary>提示</summary>

问自己："**如果同一瞬间有 100 个人点了同一个按钮，会发生什么？**"

不是所有操作都怕并发。区分标准是：
这个操作是不是"先读出来 → 在内存里算一下 → 再写回去"？

如果是，那它就有竞态。因为"读"和"写"之间，别人可能已经改过了。

</details>

---

## 第二步：排三步，并明确标出"这一步引入了什么新风险"

```text
第 1 步（新风险：                ）
第 2 步（新风险：                ）
第 3 步（新风险：                ）
```

<details>
<summary>提示</summary>

给每一步标注"新风险"而不是"新功能"，会让你的规划视角发生变化：

- "做点赞功能" → 听起来只是加个按钮；
- "引入计数竞态" → 立刻提醒你：这里需要一个原子操作，
  而且它**必须被验证**（比如快速连点，看计数对不对）。

**把风险写进任务清单，风险才会被处理。**

</details>

## 第三步：估工时，并把"验证竞态"单独列出来

```text
第 1 步：____ 小时
第 2 步：____ 小时
第 3 步：____ 小时
其中"专门验证竞态"占：____ 小时
```

<details>
<summary>提示</summary>

验证竞态很难靠"点几下"完成 —— 人手点不了那么快。
可行的办法：

- 在浏览器 Console 里写个循环，同时发 20 个请求；
- 或者用一个简单的脚本并发调用接口。

**注意：验证竞态的时间很容易被估成 0。** 因为在写代码时
它"看起来已经对了"。把它显式列进清单，才不会在最后一刻被砍掉。

</details>

## 第四步：回答一个建模问题

```text
评论应该内嵌在帖子文档里，还是单独建一个集合？
我的选择：________________
我放弃的是：______________
```

<details>
<summary>提示</summary>

没有"正确答案"，只有"你放弃了什么"。

- 内嵌：读一次就拿到全部，但**受 16MB 单文档上限约束**，
  而且评论无法独立查询；
- 拆表：无上限、可独立分页，但每次要按 `postId` 再查一次（要建索引）。

如果你能说出"我选择 X，因此放弃了 Y"，这题就答对了。
如果只说"应该拆表因为最佳实践"，等于没答。

</details>

### 并发风险扫描

| 操作 | 有竞态吗 | 为什么 |
| --- | --- | --- |
| 取帖子列表 | 否 | 纯读 |
| 取帖子详情 | 否 | 纯读 |
| 发表评论 | **轻微** | 评论本身是新增，但 `commentCount` 是读改写 |
| 点赞 / 取消 | **是** | `likeCount` 是典型的读改写，且高频 |
| 标签筛选 | 否 | 纯读 |

关键结论：**真正有竞态风险的只有两个计数字段**。

### 三步拆解

| 步骤 | 内容 | 新引入的风险 |
| --- | --- | --- |
| 第 1 步 | Comments 模块：Schema（`postId` 索引）+ 增删查接口 + 前端评论列表接真实接口 | 伪造 `postId` 评论到别人的帖子；删除权限 |
| 第 2 步 | 评论区改接真实接口 + 删除自己的评论 | 权限判断；删评论后 `commentCount` 不同步 |
| 第 3 步 | 点赞：独立的 likes 集合（记录谁赞了什么）+ `$inc` 原子更新 + 前端乐观更新对接 | **计数竞态**；重复点赞；取消时不能减成负数 |

### 顺序依据

- **先评论后点赞**：评论是新模块，可以整个独立做完并验证；
  而点赞要动已有的 posts 文档（加字段、改计数），影响面更大。
- **点赞放最后**：它是唯一需要"专门设计数据结构 + 并发验证"的部分，
  单独放在最后可以给它充足的时间，不会挤压前两步。
- **但 `comments` 的接口要在第 1 步就定死**：因为前端评论组件
  在第 2 步才接，中间这段它用的是本地数据 ——
  如果接口形状到第 2 步才想，前端的改动会翻倍。

### 关于点赞的两个设计决定

**① 为什么要单独建一个 likes 集合，而不是在 post 文档里存一个用户数组？**

存数组的写法：

```js
{ _id: postId, likedBy: ['u1', 'u2', ...] }
```

看起来简单，但有两个问题：
- 用户多起来之后数组会无限增长，最终撞上 16MB 文档上限；
- "这个人赞过没有"要扫描数组，且高并发下同一个文档会被频繁写冲突。

独立集合 `{ postId, userId }` 加**复合唯一索引**，
既解决了上限问题，又能用唯一索引天然阻止"同一个人重复点赞"。

**② 为什么 `likeCount` 用 `$inc` 而不是"读出来 +1 再写回"？**

```js
// ❌ 竞态：两个人同时读到 10，都写回 11，最终只有 11（少了一次）
post.likeCount = post.likeCount + 1
await post.save()

// ✅ 原子：数据库保证这两次 +1 都生效，最终是 12
await postModel.updateOne({ _id: id }, { $inc: { likeCount: 1 } })
```

**"读改写"是并发问题的通用信号。** 凡是你看到这种三步结构，
就该问一句："如果中间有人插进来怎么办？"

### 工时估算参考

| 步骤 | 估时 | 依据 |
| --- | --- | --- |
| 第 1 步 | 5-8 h | 新模块全套文件 + 前端接真实接口；分页与空态要补 |
| 第 2 步 | 3-5 h | 权限判断 + 计数同步 + 删除确认交互 |
| 第 3 步 | 5-8 h | 集合设计 + 唯一索引 + 原子更新 + 乐观更新的失败回滚 |
| 其中验证竞态 | **1-2 h** | 写并发脚本、观察计数、修正 |
| **合计** | **14-23 h** | 约 1 周 |

### 该砍的

> **评论的分页与楼中楼回复。**
>
> 对教学项目来说，单帖评论量不会大到需要分页；
> 而楼中楼会引入"树的深度、折叠、回复通知"一整串新问题。
>
> 明确记下来：这是一个有意识的取舍，不是遗漏。
