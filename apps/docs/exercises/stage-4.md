# 规划练习 4 · 拆解「阶段 5 · 认证与发帖」

> **规则**：先自己写完再看参考拆解。

## 这一阶段的特殊性

前面四个阶段的规划对象都是"功能"。阶段 5 不一样：
它的对象是一套**贯穿所有接口的横切机制**。

认证的特殊之处在于 **它不是一个功能，而是一个约束**：
- 加完之后，几乎所有写接口都要变；
- 它不是"做完就完了"，而是要影响已存在的代码。

> 规划这类任务时，最容易犯的错是**按"页面"拆**。
> 正确的拆法通常是按"机制"拆：先把机制立起来，
> 再让它自动作用于已有代码。

## 第一步：列出"认证会波及到哪些已有代码"

这一步不写新功能，只做**影响面盘点**。

```text
我的清单：
1.
2.
3.
4.
```

<details>
<summary>提示</summary>

从"一个请求从浏览器到数据库的路上，哪些地方会多出新的判断"去想：

```text
前端：谁需要知道"我登录了吗"？页面显示要不要变？
传输：Token 放在哪？每个请求都要带吗？
后端：哪些接口需要拦？拦下来之后"当前用户"从哪来？
数据：帖子里的作者字段，从哪来？
失效：Token 过期了怎么办？用户会看到什么？
```

**影响面盘点做不全，这个阶段就会变成"改一处漏一处"的拉锯战。**

</details>

## 第二步：排三步，并明确指出"哪一步会改动已有代码"

```text
第 1 步（验证的是：                ）  改动已有代码吗？
第 2 步（验证的是：                ）  改动已有代码吗？
第 3 步（验证的是：                ）  改动已有代码吗？
```

<details>
<summary>提示</summary>

优先做**能独立验证、且不依赖已有代码**的那一步。

如果你先做"注册登录接口"，立刻就会面临一个问题：
前端现在还没有地方存登录态，你验证不了它 ——
于是你会同时改前后端，出问题时不知道是哪边的问题。

如果先做"后端能识别 Token"这件机制上的事，
你就可以用 curl 或 Swagger 直接验证它，
**完全不需要前端参与**。等机制确认无误，再把前端接上去。

</details>

## 第三步：估工时，并单独标出"删除临时设计"的成本

阶段 3 留了一个临时设计：帖子的作者由客户端提交（`authorId` / `authorUsername`）。

```text
第 1 步：____ 小时
第 2 步：____ 小时
第 3 步：____ 小时
其中"删除临时作者字段"占：____ 小时
```

<details>
<summary>提示</summary>

删除一个临时设计，成本往往**远高于**"删掉那两行"：

1. 后端 DTO 里去字段 → Service 里改数据来源 → 单测跟着改；
2. 前端的发帖页要停止发送这两个字段；
3. 已有的测试数据里 author 是客户端传的，改完之后语义变了。

**这正是"临时方案"的真实代价：它不是免费的，只是把成本延后了。**
把这项成本显式估出来，是排期能力里很实际的一课。

</details>

## 第四步：说出一个"如果你不做，用户会看到什么"的场景

```text
场景：____________________________
用户看到：________________________
你为什么决定（做 / 不做）它：________
```

<details>
<summary>提示</summary>

最典型的候选是 **Access Token 过期后的静默续期**。

- 不做：用户每隔 15 分钟被踢回登录页，而且是在他点"发布"的那一刻；
- 做：用户完全无感。

它不难，但很容易被"先把功能做完再说"挤掉。
**明确地决定"不做"，和忘记做，是两回事。**

</details>

### 三步拆解

| 步骤 | 内容 | 验证的是 | 改动已有代码 |
| --- | --- | --- | --- |
| 第 1 步 | 后端：users 模块 + 注册/登录接口 + 密码哈希；用 Swagger 验证 | 密码是否安全落库、Token 能否签发 | 否（纯新增） |
| 第 2 步 | 后端：守卫 + 当前用户装饰器；改造 `POST /posts` 用 Token 里的用户；同步改单测 | 未登录能否访问受保护接口（应 401） | **是** |
| 第 3 步 | 前端：`useAuth` + `useApi` 注入 Token + 401 续期 + 路由守卫 + 头部与发帖页改造 | 用户无感续期、未登录被拦 | **是** |

### 顺序依据

- **先用 Swagger/curl 把后端机制验证透，再接前端**。
  这样"后端机制对不对"和"前端接得对不对"是两个独立问题，
  不会互相掩盖。
- **第 2 步必须比前端早**：如果先做前端登录态，
  前端会去调还不存在的受保护接口，你会在两个方向同时调试。
- **删除临时作者字段放在第 2 步内**，因为它是同一次改动的一部分：
  一旦有了"当前用户"，客户端提交作者就没有意义了。

### 工时估算参考

| 步骤 | 估时 | 依据 |
| --- | --- | --- |
| 第 1 步 | 5-8 h | users/auth 两个模块 8 个文件；bcrypt 的异步用法、邮箱唯一索引冲突的处理都要查 |
| 第 2 步 | 4-7 h | 守卫 + 装饰器 + DTO 改造 + 已有单测跟着改（这部分常被低估） |
| 第 3 步 | 6-10 h | `useApi` 的 401 重试要处理"并发请求同时过期"的情况，容易写出竞态 |
| 其中删除临时字段 | 1-2 h | 看起来只是删两行，实际要动 DTO / Service / 单测 / 前端表单 |
| **合计** | **16-27 h** | 约 1-1.5 周 |

### 该"决定不做"的

> **Refresh Token 的主动失效（服务端存一份、支持踢人下线）。**
>
> 它需要给 Refresh Token 单独建集合、加索引、加清理逻辑。
> 对教学项目来说收益很小 —— 你只需要"能续期"，
> 不需要"能远程注销某个设备"。
>
> **但要明确地写下来**：这是一个有意识的取舍，不是遗漏。
> 这样将来真的需要时，你知道自己当时为什么没做。

</details>
