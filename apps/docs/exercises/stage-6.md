# 规划练习 6 · 拆解「阶段 7 · AI 能力」

> **规则**：先自己写完再看参考答案。

---

## 这一阶段的特殊性

前面所有功能，都是"你写什么，它就不会给你意外"。
而 LLM 是一个**会失败、会变慢、会给出你不想要的东西**的外部依赖。

> 所以在规划这个阶段时，最重要的一步不是"列出功能点"，
> 而是**先想清楚它失败了会怎样**。

---

## 第一步：写下"AI 会怎么失败"

不要写功能，只写失败模式。尽量穷举。

```text
我的清单：
1.
2.
3.
4.
5.
```

<details>
<summary>提示：从"调用一次 LLM 会经过哪些环节"出发</summary>

```text
网络 → 鉴权 → 服务端排队 → 模型生成 → 返回 → 解析
```

每个环节都能出问题：

- 网络断了 / 超时；
- API Key 过期或额度用尽；
- 服务商限流；
- 模型返回了**不符合预期格式**的内容；
- 返回内容对但**超出长度限制**（比如生成 500 字的摘要）；
- 返回了不在白名单里的标签。

最后两条最容易被忽略 —— **它们不是"失败"，而是"成功但结果不可用"**。

</details>

---

## 第二步：对每种失败，决定"用户看到什么"

这一步才是真正的设计。

```text
超时            → 用户看到：
返回格式不对    → 用户看到：
标签不在白名单  → 用户看到：
API Key 失效    → 用户看到：
```

<details>
<summary>提示</summary>

有一类答案是"用户什么都不该知道"，另一类是"必须让用户看到"。

判断标准：**这件事影响用户的核心目标吗？**

- 摘要没生成 → 不影响他"文章发布成功"的目标 → 静默降级；
- 文章没发出去 → 影响核心目标 → 必须明确报错。

**把这两类混在一起处理，是 AI 功能最常见的工程失误。**

</details>

---

## 第三步：排三步，并明确"每步结束时怎么验证"

AI 功能最难验证的地方是：**它的输出是不确定的**。
所以验证方式必须提前设计。

```text
第 1 步（怎么验证：                ）
第 2 步（怎么验证：                ）
第 3 步（怎么验证：                ）
```

<details>
<summary>提示</summary>

关键技巧：**想办法让"失败"变得可复现**。

不能复现的失败等于没有验证。可行做法：

- 把 API Key 改成一个明显错误的字符串 → 验证降级路径；
- 把超时设成 1 毫秒 → 验证超时路径；
- 在 Prompt 里故意要求一个非法输出 → 验证解析失败路径。

**"我试了三次都能出摘要"不等于验证通过** ——
它只证明这三秒里网络是好的。

</details>

---

## 第四步：估工时，并把"降级路径"单独列出来

```text
第 1 步：____ 小时
第 2 步：____ 小时
第 3 步：____ 小时
其中"实现并验证降级路径"占：____ 小时
```

<details>
<summary>提示</summary>

降级路径的代码量很小（几个 try/catch + 字段留空），
但**验证它需要的时间往往是写它的两三倍**。

如果你不把它单独列出来，它就会被"先把主流程做完"挤掉 ——
然后上线后第一次 API 抖动，用户看到的就是一片报错。

</details>

## 参考拆解（写完再看）

<details>
<summary>点开对照</summary>

### 失败模式清单

| 失败 | 原因 | 是否影响核心目标 |
| --- | --- | --- |
| 网络超时 | 服务商慢 / 网络抖动 | 否 |
| 鉴权失败 | Key 过期、额度用尽 | 否 |
| 限流 429 | 调用过频 | 否 |
| 返回非 JSON | 模型"自由发挥" | 否 |
| JSON 结构不对 | 少字段、字段类型错 | 否 |
| 字段超长 | 摘要写了 500 字 | 否 |
| 标签不在白名单 | 模型编了个新标签 | 否 |
| **发帖本身失败** | 数据库问题 | **是** |

关键结论：**AI 的所有失败都不影响核心目标。**

### 三步拆解

| 步骤 | 内容 | 怎么验证 |
| --- | --- | --- |
| 第 1 步 | 把 AI 调用做成一个独立服务：Prompt 模板 + 结构化输出 Schema + 超时；先用一个最小脚本式调用验证能拿到合法 JSON | 直接调用一次，把返回的 JSON 打印出来人工确认 |
| 第 2 步 | 接进发帖流程，但**放在落库之后**（异步旁路），失败只记日志 | 把 Key 改错 → 发帖**依然成功**，只是没有摘要 |
| 第 3 步 | 结果落库前的二次校验：标签过滤到白名单内、摘要截断到上限、超长则丢弃 | 伪造一个超长结果，确认被截断而不是写进数据库 |

### 顺序依据

- **第 1 步先脱离业务单独验证 LLM 调用**。因为 LLM 的返回格式
  是最大的不确定性来源，把它隔离出来，你才知道问题出在"调用"还是"集成"。
- **第 2 步刻意把调用放在落库之后**。这是整个设计的关键：
  如果先调 AI 再落库，那么 AI 慢 10 秒，用户的发帖就慢 10 秒；
  AI 挂了，用户的文章就发不出去 —— **AI 变成了核心链路的单点故障**。
- **第 3 步必须做**。永远不要信任外部输入，LLM 的输出就是外部输入。

### 工时估算参考

| 步骤 | 估时 | 依据 |
| --- | --- | --- |
| 第 1 步 | 3-6 h | 要读 LangChain 与智谱的接入方式、确认包名与导入路径、处理鉴权；结构化输出要调几次 Prompt 才稳定 |
| 第 2 步 | 2-4 h | 改动面很小（就几行），但要处理"旁路不阻塞"与日志 |
| 第 3 步 | 2-3 h | 校验与截断逻辑简单，但边界条件多 |
| 其中验证降级 | **2-3 h** | 要分别构造超时、鉴权失败、非法输出三种场景 |
| **合计** | **9-16 h** | 约 3-5 天 |

### 该砍的

> **流式输出（打字机效果）与重试机制。**
>
> 流式输出会让用户等待感更好，但它需要改用 SSE、改造前端渲染、
> 处理中断与重连 —— 一整套新的复杂度。
> 而本项目的 AI 是**旁路**：用户根本不需要等它，所以流式的收益为零。
>
> 重试的意义也不大：摘要生成失败，最坏结果是"这篇没有摘要"，
> 而不是"用户被阻塞"。为一个非关键路径加重试，是在给系统增加不确定性。

### 一个容易被漏掉的规划项

**日志里绝不能出现 API Key 和完整正文。**

这要写进任务清单，而不是"记得注意一下"。
因为出问题时你最想做的事就是"把请求打出来看看" ——
而那一行 `console.log` 很可能就带着你的密钥。

正确做法是：日志只记**错误码、耗时、正文长度**，不记正文内容。

</details>
