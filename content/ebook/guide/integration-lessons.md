# 集成经验：从接口到浏览器，中间隔着什么

> 这一页记录的是一次**看起来已经做完、实际上根本没在工作**的功能开发：
> GitHub 热门项目榜 + AI 学习助手，外加一次全站前端重构。
>
> 它第一次被宣布"完成"时是这样的：页面能打开、数据都在、卡片都渲染了 ——
> 但**所有按钮都是死的**。不打开控制台，你完全看不出它坏了。
>
> [部署篇](./deployment-lessons) 讲"上线会撞上什么"，[调试篇](./debugging-lessons) 讲"按什么顺序找原因"。
> 这一篇讲第三件事：**同一份代码在「开发 / 构建 / 浏览器」三个位置运行时，会在哪里悄悄失效。**

## 一、契约两端不一致：报错出现在离成因最远的地方

**现象**：点卡片上的「问 AI」，必定返回 400。而同一个接口用 curl 手测是好的。

**原因**：共享类型里 `RepoQuestionContext` 带着 `type: 'repo'` 字段，前端确实会发过来；
但后端 DTO 没有声明它，而全局校验开了 `forbidNonWhitelisted` —— 多一个未声明字段就是 400：

```json
{"statusCode":400,"details":["context.property type should not exist"]}
```

**为什么难查**：报错只说"多了一个字段"，它不会说"你的契约两端不一致"。
而 `type` 在前端是**有意为之的设计**（给未来的扩展留判别字段），
在后端却只是"一个没人认识的垃圾字段"。

**怎么修**：契约两端只能"都留"或"都删"，不能一端有一端无。
这里选择留 —— 在 DTO 里补上可选字段，并在注释里写明**为什么后端不读它也必须声明**。

> **共享类型的价值是"改一处、两端同时报错"，但这个前提是两端都真的用了它。**
> 只要有任何一端是"手写 DTO + 手写校验"，漂移的可能性就一直存在。
> 每次新增请求体字段时，多问一句：**另一端声明了吗？**

#### 实现方法

本项目把接口字段只在 `packages/shared` 定义一次，前后端都 import 同一份；新增请求体字段时，两端（DTO 与共享类型）必须同时声明或同时删除。全局校验开 `forbidNonWhitelisted`。

#### 原理

契约漂移源于"一端手写 DTO、另一端手写校验"，两份定义从此各走各路。共享类型把字段定义收口到一处，任一方漏了就在编译期报错；而 `forbidNonWhitelisted` 在运行期把"多一个未声明字段"直接变成 400，逼出漂移。

#### 与相关技术栈的关系

和 OpenAPI、Swagger 集中描述契约相比，共享类型把契约放进代码、随类型系统检查，更贴近"契约先行"；OpenAPI 更适合需要给外部方看的文档。和 GraphQL（Schema 即契约、由框架强制）相比，REST 的契约更靠约定，所以更需要共享类型兜底。

#### 面试常见问题与解题思路

**Q1：前后端字段对不上，怎么排查？**
怎么想：从"契约两端"切入。怎么答：看报错是 400 多字段，确认两端声明是否一致；共享类型能直接让漂移在编译期暴露。追问：为什么 `forbidNonWhitelisted` 会把多余字段变 400？

**Q2：怎么保证前后端契约一致？**
怎么想：从"单一事实来源"切入。怎么答：共享类型包加运行时校验双保险。追问：OpenAPI 和共享类型各适合什么场景？

## 二、只有真实浏览器能发现的那种失效

**现象（本次最严重）**：页面上该有的全都有 —— 标题、列表、卡片、数据，一切正常。
但**点任何按钮都没反应**：切换时间范围、打开抽屉、点「问 AI」，全部静止。

**真实原因**：整页客户端 JS 根本没跑起来。

```text
SyntaxError: The requested module '.../packages/shared/dist/index.js'
  does not provide an export named 'avatarGradientClass'
```

共享包编译出来是 **CommonJS**（NestJS 必须跑 CJS），而浏览器只认 **ESM**。
Vite 默认**不预打包 workspace 链接包**，于是这个 CJS 文件被当成源码直接送进浏览器，
只能靠"静态导出识别"兜底 —— 而新增一个导出之后，识别没跟上。
模块加载抛错 → **水合（hydration）整体失败** → 所有交互失效。

**为什么它特别难发现**：

| 你看到的 | 真相 |
| --- | --- |
| 页面完整、布局正常 | 那是 SSR 渲染出来的 HTML |
| 数据正确、卡片有内容 | 那是服务端取的，与客户端无关 |
| 不点按钮看不出异常 | 只有打开控制台才看得到那行 SyntaxError |
| 接口测试全绿 | 接口本来就没问题 |

**修法**：让 Vite 强制预打包共享包，交给 esbuild 做完整的 CJS → ESM 转换：

```ts
// apps/web/nuxt.config.ts
vite: {
  optimizeDeps: { include: ['@studyplan/shared'] },
}
```

> **SSR 应用有一个特殊的盲区：服务端渲染的 HTML 会掩盖客户端的失败。**
> "页面能看"和"页面能用"是两件独立的事，而前者会把后者的问题藏得严严实实。
> 只要前端有较大改动，就必须在**真实浏览器里点一遍** —— 不能只看页面打不打得开。

#### 实现方法

本项目让 Vite 强制预打包共享包：`vite: { optimizeDeps: { include: ['@studyplan/shared'] } }`，交给 esbuild 做完整 CJS 到 ESM 转换，避免把 CJS 文件直接送进浏览器。

#### 原理

NestJS 必须跑 CommonJS，共享包编译成 CJS；浏览器只认 ESM。Vite 默认不预打包 workspace 链接包，于是 CJS 文件被当源码直送浏览器，模块加载抛错导致水合整体失败。SSR 渲染的 HTML 掩盖了客户端失败，所以"页面能看"和"页面能用"是两件事。

#### 与相关技术栈的关系

和 webpack 的 `transpileDependencies` 思路一致：把 Node 生态的包也纳入转换。和只做 CSR 的项目相比，SSR 多了"服务端 HTML 掩盖客户端错误"的盲区。和 esbuild、rollup 的 ESM 输出相比，CJS 是 Node 历史包袱，需显式转换。

#### 面试常见问题与解题思路

**Q1：页面正常但按钮都没反应，可能是什么原因？**
怎么想：从"SSR 掩盖客户端失败"切入。怎么答：客户端 JS 没跑起来（如模块加载错误导致水合失败）。追问：怎么确认是水合失败而不是业务逻辑问题？

**Q2：CJS 和 ESM 混用会有什么坑？**
怎么想：从"模块格式"切入。怎么答：浏览器不认 CJS，未转换的 CJS 进浏览器会 SyntaxError，整页交互失效。追问：monorepo 里怎么统一模块格式？

## 三、构建期产物：本地能跑不等于线上能跑，反过来也成立

**现象**：问 AI "这段代码为什么这样写"，它回答"资料中没有提到"。

**原因**：喂给模型的"本站代码索引"是一个**构建期产物**，
而生成它的那一步**只写在 `Dockerfile.vercel` 里**：

```dockerfile
RUN pnpm --filter @studyplan/api build
RUN node scripts/generate-code-index.mjs   # ← 只有容器构建会执行这一行
```

本地跑 `pnpm build` 不会执行它 → 索引文件不存在 → 检索不到任何文件。
**不报错、不崩溃**，只是答案悄悄退化成"没查到"。

**修法**：把它并进包自己的构建脚本，让本地与容器**走同一条路径**：

```json
"build": "nest build && node ../../scripts/generate-code-index.mjs"
```

> 同一个动作被写在两个地方（一个在 Dockerfile、一个"本该在" package.json），
> 就是这类 bug 的温床。
> **只要一个步骤在「本地」和「线上」走的是不同代码路径，它们迟早会分叉。**

#### 实现方法

本项目把代码索引生成并进 API 包的构建脚本：`"build": "nest build && node ../../scripts/generate-code-index.mjs"`，让本地与容器走同一条路径，不留"只在 Dockerfile 里才执行"的步骤。

#### 原理

当某个步骤"只在线上构建才执行"时，本地和线上走了不同代码路径，行为迟早分叉。索引没生成不报错、不崩溃，只是答案悄悄退化。把步骤并进统一构建脚本，配合"启动即预热"加载索引，缺文件会在启动日志立刻暴露。

#### 与相关技术栈的关系

和 CI 里单独跑的构建步骤相比，把步骤收进包脚本能保证本地也执行。和"配置即代码"一致：同一套动作只写一处。和缓存或编译产物目录（如 `dist/`）相比，自生成的数据产物更隐蔽，容易漏跑。

#### 面试常见问题与解题思路

**Q1：本地能跑线上报错（或反过来），怎么定位？**
怎么想：从"代码路径是否一致"切入。怎么答：先查两边构建脚本是否相同，有无"只在某处执行"的步骤。追问：怎么让本地和线上构建路径统一？

**Q2：为什么"不报错"的退化最危险？**
怎么想：从"无信号"切入。怎么答：失败没有异常，只会悄悄变糟，排查无从下手。追问：怎么把这类静默失败变可见？

**顺带补了一处可观测性**：索引加载原本是"第一次提问时才惰性加载"，
现改为**启动即预热** —— 缺文件会在**启动日志**里立刻显示出来，
而不是等用户问出一个答不出的问题、再去猜为什么。

## 四、外部 API：不要按名字猜性能

**现象**：AI 问答频繁超时，且波动很大 —— 同一个问题，有时 19 秒，有时超过 60 秒。

**原因**：默认模型叫 `deepseek-ai/deepseek-v4-flash-0731`，名字里有 "flash"。
但实测它的返回结构是：

```text
content=58字   reasoning=508字   completion_tokens=316
```

它是**推理模型** —— 先写一大段思考链，再产出很短的答案。
简单问题 22 秒，问题一复杂就直接撞上超时上限。
**"flash" 只描述它的定位，不代表延迟低。**

**怎么选模型**：拿**真实负载**实测，而不是看名字。
同一段中文问答 prompt 的实测对比：

| 模型 | 耗时 | 产出正文 | 思考链 |
| --- | --- | --- | --- |
| `openai/gpt-oss-20b` | 20.6s | 747 字（≈ **36 字/秒**） | 339 字 |
| `google/gemma-4-31b-it` | 25.4s | 590 字（≈ 23 字/秒） | 0 |
| `deepseek-ai/deepseek-v4-flash-0731` | 22s（简单问题） | 58 字 | **508 字** |
| `z-ai/glm-5.3-flash` | **>70s 超时** | — | — |
| `meta/llama-3.3-70b-instruct` | **410 Gone** | — | — |

**关键指标不是"总耗时"，而是"产出速度"**（正文字数 ÷ 秒）——
因为超时只跟"要生成多少字"有关。

#### 实现方法

本项目用真实中文问答负载实测候选模型，看"正文字数 ÷ 秒"而非总耗时；默认模型走 `NVNIM_MODEL` 环境变量、不写死。推理模型的 `max_tokens` 要同时装下思考链与正文。

#### 原理

"flash"只描述定位不代表延迟低；推理模型先写思考链再给短答案，总耗时被思考链撑大，但超时只跟要生成的正文量有关。所以关键指标是正文产出速度，而非包含排队和首字延迟的总耗时。

#### 与相关技术栈的关系

和"按模型名气选"相比，实测产出速度更贴体验。和纯总耗时评估相比，区分首字延迟与正文速度是更准的预测。和把模型写死相比，可配置模型名让"模型下线"从故障变一次环境变量变更。

#### 面试常见问题与解题思路

**Q1：选 LLM 看什么指标？为什么不是总耗时？**
怎么想：从"超时来源"切入。怎么答：超时只跟正文量相关，总耗时混入排队与首字延迟。追问：推理模型为什么对 max_tokens 更敏感？

**Q2：模型该写死还是可配置？**
怎么想：从"会变的标识"切入。怎么答：模型会下线，配成变量并翻译上游 410 错误最稳。追问：怎么把上游错误翻成用户可操作提示？

## 五、模型会下线，所以模型名不能写死

本次实测中，**三个**模型返回 `410 Gone`：

```text
The model 'meta/llama-3.1-8b-instruct' has reached its end of life
on 2026-08-26T09:00:00Z and is no longer available.
```

（写这段注释期间又接连踩到 `nvidia/nemotron-3-nano-30b-a3b`、`meta/llama-3.3-70b-instruct`）

所以模型名必须**可配置**（`NVNIM_MODEL`），并且遇到 410/404 时要把上游的语义
**翻译成人能直接照做的提示**：

```text
模型「xxx」已下线或不存在，请在环境变量 NVNIM_MODEL 中更换一个可用模型
```

而不是把 `410` 原样甩给用户 —— 用户看到状态码只能猜。

> **凡是"会变的标识"都该做成配置**：模型名、API 版本、端点。
> 写死的时候它一定能用，问题只在"哪天突然不能用了"，而且不会有任何预警。

#### 实现方法

本项目模型名走 `NVNIM_MODEL` 环境变量，遇到 410 或 404 时把上游语义翻译成"请在 NVNIM_MODEL 换一个可用模型"，而不是甩状态码。

#### 原理

上游模型会下线（`410 Gone`），写死会在某天无声失效。把"会变的标识"（模型名、API 版本、端点）做成配置，失败可切换；同时把上游技术错误翻译成人能照做的提示，降低用户排查成本。

#### 与相关技术栈的关系

和硬编码相比，配置化让外部依赖可替换。和 fail-fast（缺核心依赖直接崩）相比，可选依赖降级更友好。和 Feature Flag 类似：用外部开关控制行为而不改代码。

#### 面试常见问题与解题思路

**Q1：外部依赖会下线，怎么设计才稳？**
怎么想：从"可替换"切入。怎么答：标识配置化、错误翻译为可操作提示、必要时降级。追问：降级时怎么让用户知情？

**Q2：上游返回 410 或 404 该怎么处理？**
怎么想：从"语义翻译"切入。怎么答：不要原样抛状态码，翻译成"换一个模型"这类动作。追问：怎么避免每次上游变动都改代码？

## 六、检索：中文必须分词，重复的词不能重复计分

问 AI"热门榜单的缓存和降级是怎么实现的"，
**真正实现了缓存的那个文件却没有进入参考资料**。

两个互相独立的算法缺陷：

### 缺陷 1 · 中文没有分词

```ts
// 问题写法：整段连续汉字被当成"一个关键词"
const chinese = lower.match(/[一-龥]{2,}/g) ?? []
// "榜单的后端缓存是怎么设计的" → 一个 12 字的词
// 而文件路径里不可能出现这么长的串 → 这个"关键词"永远命不中任何文件 → 等于白提
```

改成 **2 字滑窗**：

```ts
// "榜单缓存" → "榜单" / "单缓" / "缓存" ...
```

滑窗会产生一些碎片词（"单缓"），但它们命不中任何文件，**代价近乎为零**；
而"缓存""刷新"这类真词一旦命中，就是区分同目录文件的**决定性一票**。

### 缺陷 2 · 重复出现的词被重复计分

问题里 "GitHub" 出现了两次 → `github` 被加了两次分 →
`github.client / github.controller / github.module` 这些
"**路径含 github、但摘要与缓存无关**"的文件被刷到并列第一，
把真正相关的 `github.service.ts` 挤出了 topK。修法是**关键词去重**。

修复前后对比（同一个问题）：

| 文件 | 修复前 | 修复后 |
| --- | --- | --- |
| `github.service.ts` | 11 分（**第 5，被挤掉**） | **11 分（第 1）** |
| `packages/shared/src/types/github.ts` | 15 分（第 1） | 9 分 |
| `github.controller.ts` | 13 分 | 7 分 |

### 还有一处不是代码问题

`github.service.ts` 的**文件头没有写说明注释**，索引只能取到它第 10 行某个常量的注释，
于是摘要变成"缓存软过期时间的默认值"—— 完全没有描述这个文件是干什么的。

补上文件头说明之后，摘要才真正有了检索价值。

> 这印证了那个索引脚本的设计前提：**本项目极高的注释密度，本身就是最好的检索依据。**
> 注释写得越像"这个文件负责什么"，检索就越准 ——
> 而这一点靠算法补不回来，它取决于**写代码时的习惯**。

#### 实现方法

本项目中文检索用 2 字滑窗把连续汉字切成"榜单""缓存"等词，并对关键词去重计分；被检索的源文件补清晰文件头说明，提升摘要质量。

#### 原理

整段连续汉字被当成一个关键词，永远命不中文件路径；2 字滑窗虽产生碎片词但代价近乎零，真词命中则是决定性一票。重复出现的词被重复计分，会把"路径含该词但无关"的文件刷到前面，去重后才能命中真正相关的文件。

#### 与相关技术栈的关系

和专业中文分词（jieba、IK）相比，2 字滑窗是轻量近似，适合代码检索这种短文本。和英文按空格分词相比，中文无词边界，必须显式切分。和向量检索相比，关键词匹配更简单、可解释，适合"找文件"这类任务。

#### 面试常见问题与解题思路

**Q1：中文全文检索为什么要分词？**
怎么想：从"无词边界"切入。怎么答：中文没有空格，整句当关键词命不中；需切成词再匹配。追问：2 字滑窗有什么优缺点？

**Q2：关键词重复出现为什么要去重？**
怎么想：从"计分失真"切入。怎么答：重复词被重复加分，会推高路径含该词但无关的文件。追问：除了去重，还有哪些检索优化点？

## 七、受控浮层：`v-model` 不生效时，改用显式挂载

**现象**：点浮动按钮，状态**确实变了**（`aria-label` 从"打开 AI 助手"变成"关闭 AI 助手"），
但抽屉**一个节点都没有输出**，控制台也不报错。

**临时解法**：把 `v-model="open"` 改成**"挂载"与"展开"分离**：

```vue
<!-- 由 v-if 决定何时挂载，显式把 open 置真，不再依赖组件内部对状态的转发 -->
<USlideover v-if="open" :open="true" side="right" ...>
```

> 组件行为与预期不符**且不报错**时，"绕过它"往往比"继续读它的源码"更快。
> 但一定要在代码里写清**为什么绕** —— 否则下一个人会以为这是随手写的。

---

## 八、把这一页压成一份检查清单

**契约一致性**

- [ ] 新增请求体字段时，另一端（DTO / 共享类型）声明了吗
- [ ] 全局校验开着 `forbidNonWhitelisted` 吗（它会把"多一个字段"直接变成 400）
- [ ] 共享类型与 DTO 是"都留"还是"都删"，**不要一端有一端无**

**构建一致性**

- [ ] 构建期产物（索引、清单、静态资源）在**本地**也会生成吗
- [ ] 同一个动作是否被写在两个地方（Dockerfile 与 package.json 各一份）

**前端可交互性**

- [ ] 改动后是否在**真实浏览器**里点过一遍（而不是只看页面能不能打开）
- [ ] 控制台有报错吗（**SSR 会掩盖客户端失败**）
- [ ] workspace 依赖的模块格式，与预打包配置对得上吗

**外部服务**

- [ ] 选模型/供应商时，是否用**真实负载**测过，而不是按名字猜
- [ ] 所有"会变的标识"（模型名、版本、端点）是否都做成了配置
- [ ] 上游返回的"已下线/已废弃"是否翻译成了能直接照做的提示

**检索与提示词**

- [ ] 中文检索做了分词吗（整段汉字不等于关键词）
- [ ] 计分会不会因为"同一个词出现多次"而失真
- [ ] 被检索的源文件，有清晰的**文件头说明**吗

**一句话总结**

> 这次真正花掉时间的，不是"写出功能"，而是**发现功能根本没在工作** ——
> 而它伪装成了"一切正常"。
>
> 凡是"看起来对"的地方，都要找一个**独立于实现者预期**的证据去验证：
> 浏览器里的实际点击、日志里的实际输出、接口返回里的实际字段。
> **你写的代码不构成证据，"它在你眼前真的动了"才算。**
