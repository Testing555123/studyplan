## 二、核心概念

### 1. 评论为什么必须是独立集合

内嵌写法看起来更自然：

```js
{ title: '...', comments: [ {...}, {...} ] }
```

但它有一个硬性天花板：**MongoDB 单个文档最大 16MB**。
一条热门帖子的评论迟早会把这个空间撑爆 —— 而那天到来时，
表现是"这篇帖子的评论突然发不出去了"，且不会有任何预警。

独立集合没有这个上限，还带来额外好处：评论可以独立分页、独立删除，
写入时也不会锁定整个帖子文档。

代价是每次要按 `postId` 再查一次 —— 所以**必须有 `postId` 索引**。
没有索引的代价不是"慢一点"，而是"每条评论都要扫全集合"。

#### 实现方法

本项目把评论放在独立的 `comments` 集合，按 `postId` 查询并建索引，不再内嵌进帖子文档。列表、删除、分页都针对该集合操作，不再锁定帖子文档。

#### 原理

MongoDB 单文档有 16MB 上限，热门帖子的评论内嵌进去迟早撑爆，且那天到来时表现是"评论突然发不出去"且无预警。独立集合消除了这个天花板，还让评论可独立分页、独立删除、独立写入而不锁整个帖子。代价是每次要按 `postId` 再查一次，所以必须有 `postId` 索引，否则每条评论都要扫全集合。

#### 与相关技术栈的关系

和关系型数据库的"评论表加外键 post_id"思路一致，本质都是"一对多拆表"。和文档内嵌相比，独立集合牺牲一点查询便利换来了规模上限与写入并发。和分桶（按帖子把评论拆成多个子集合）相比，本项目规模用单一集合加索引足够，不必过早优化。

#### 面试常见问题与解题思路

**Q1：评论为什么不内嵌进帖子？**
怎么想：从"文档上限与写入并发"切入。怎么答：内嵌有 16MB 天花板、会锁文档、不利分页；独立集合可扩展。追问：什么情况下内嵌反而合适？（一对少且只读的关联）

**Q2：独立集合后怎么保证查询不慢？**
怎么想：从"索引"切入。怎么答：在 `postId` 上建索引，按帖子分页查；缺索引会全集合扫描。追问：评论还要按时间排序，索引怎么设计？

### 2. 点赞为什么要用独立集合 + 复合唯一索引

直觉写法是在帖子上存一个数组：

```js
{ _id: postId, likedBy: ['u1', 'u2', ...] }
```

两个致命问题：

1. **数组无限增长**，最终撞上 16MB 上限；
2. **高并发下写冲突**：每次点赞都改同一个文档，MongoDB 对单文档的写入是串行的。

独立集合把"一条点赞"变成一行记录，两个问题同时消失。而那"一个人不能重复点赞"
靠什么保证？靠**复合唯一索引**：

```ts
LikeSchema.index({ postId: 1, userId: 1 }, { unique: true })
```

> **这个索引不是性能优化，它是业务规则的执行者。**

#### 实现方法

本项目把"一条点赞"存为 `likes` 集合里的一行记录：`{ postId, userId, ... }`，并在 `{ postId: 1, userId: 1 }` 上建唯一索引。`like()` 直接插入，捕获唯一冲突即表示已赞过。

#### 原理

直觉写法是在帖子上存 `likedBy` 数组，但它有两大问题：数组无限增长撞 16MB 上限；高并发下每次点赞都改同一文档，单文档写入串行、易冲突。独立集合把"一条点赞"变成一行，两个问题都消失。"一个人不能重复点赞"这个规则，靠复合唯一索引在数据库层强制执行。

#### 与相关技术栈的关系

和关系型数据库的"点赞表加 (user_id, post_id) 唯一约束"完全对应，都是用数据库约束保证不重复。和内存计数器或 Redis Set 相比，MongoDB 集合更直接、无需额外组件。这条索引不是性能优化，而是业务规则的执行者，应用层检查在并发下不可靠。

#### 面试常见问题与解题思路

**Q1：点赞数据怎么建模才能防重复？**
怎么想：从"数据库约束"切入。怎么答：独立集合加 (postId,userId) 唯一索引，让插入冲突成为"已赞过"的信号。追问：应用层先查再插为什么不行？（TOCTOU 竞态）

**Q2：为什么不用数组存点赞用户？**
怎么想：从"规模与并发"切入。怎么答：数组有 16MB 上限、单文档并发写入串行。追问：用户量极大时独立集合怎么扩展？

### 3. 正确性交给有约束能力的那一层

有了上面的唯一索引，服务层就**不需要**"先查有没有赞过"：

```ts
// ❌ 有并发漏洞：两个人可能同时查到"没赞过"，然后都去插入
const exists = await likeModel.findOne({ postId, userId })
if (exists) throw new ConflictException()

// ✅ 直接插，让数据库裁决
try {
  await likeModel.create({ postId, userId })
} catch (error) {
  if (isDuplicateKeyError(error)) { /* 已经赞过了 */ }
}
```

"查"和"插"之间有一个时间窗口。应用层的检查只能用来
"给出更友好的提示"，**不能用来保证正确性**。

> 一条通用原则：**正确性交给有约束能力的那一层去做。**
> 并发场景下，能提供约束的只有数据库。

#### 实现方法

本项目点赞服务不"先查有没有赞过"，而是直接 `likeModel.create({ postId, userId })`，捕获重复键错误就当作"目标状态已达成"返回成功。查重交给唯一索引。

#### 原理

"先查再插"在查与插之间有一个时间窗口，两个并发请求可能同时查到"没赞过"然后都插入，应用层检查只能给友好提示、不能保证正确性。能提供约束的只有数据库，所以把正确性交给唯一索引这一层。

#### 与相关技术栈的关系

和乐观锁（带版本号更新）相比，唯一索引适合"存在性或唯一性"这类约束；和数据库事务相比，单条插入的约束更轻量。和"先读后写"的通用模式相比，这里用"试错加捕获冲突"替代，避免 TOCTOU 窗口。分布式环境下这类"让存储裁决"的思路也很常见。

#### 面试常见问题与解题思路

**Q1：为什么不能先查再插入来防重复？**
怎么想：从"竞态窗口"切入。怎么答：查与插之间有时间差，并发下两人都查到"无"然后都插入。追问：这叫什么问题？（TOCTOU、检查时间与使用时间不一致）

**Q2：应用层校验和数据库约束怎么分工？**
怎么想：从"谁能保证正确性"切入。怎么答：应用层做友好提示，数据库约束做最终正确性保证。追问：唯一索引冲突时怎么返回友好信息？

### 4. `$inc` 与 `$max`：解决"读改写"竞态

```ts
// ❌ 读 → 改 → 写：两个人同时读到 10，都写回 11，两次点赞只涨了 1
post.likeCount = post.likeCount + 1
await post.save()
```

```ts
// ✅ 让数据库做加法，中间不给别人插队的机会
{ $inc: { likeCount: 1 } }
```

但 `$inc: -1` 有个副作用：计数已经是 0 时会变成 **-1**。
一个"-1 个赞"的界面比少一个赞难看得多，而且它会一直留在数据库里。

所以本项目用的是**聚合管道更新**，在数据库里同时完成加法和兜底：

```ts
[ { $set: { likeCount: { $max: [0, { $add: ['$likeCount', delta] }] } } } ]
```

一句话：**`$inc` 保证不丢更新，`$max` 保证不出负数。**

#### 实现方法

本项目用聚合管道更新在数据库内完成计数：`{ $set: { likeCount: { $max: [0, { $add: ['$likeCount', delta] }] } } }`，`delta` 为 +1 或 -1。它把加法和"不低于 0"的兜底放在同一次数据库操作中。

#### 原理

"读出来加 1 再写回"有竞态：两人同时读到 10，都写回 11，两次点赞只涨 1。让数据库用 `$inc` 做加法，中间不给人插队，更新才不丢失。但 `$inc: -1` 在计数已是 0 时会变成 -1，且永远留在库里。所以再用 `$max: [0, ...]` 在数据库层兜底，保证不出负数。

#### 与相关技术栈的关系

和 Redis 的 `INCR`/`DECR` 原子计数相比，MongoDB 的 `$inc` 同样是原子操作，但 `$inc` 单用无法兜底负数。和"应用层加锁"相比，数据库原子更新无需分布式锁、粒度更细。和 SQL 的 `UPDATE t SET c = c + 1 WHERE ...` 语义一致，都是服务端计算避免读改写。

#### 面试常见问题与解题思路

**Q1：`$inc` 和"读出来加 1 再写回"本质区别？**
怎么想：从"原子性"切入。怎么答：`$inc` 由数据库原子执行，无读改写窗口；读改写并发会丢更新。追问：高并发下读改写会丢几次更新？

**Q2：取消点赞为什么不能直接 `$inc: -1`？**
怎么想：从"负数"切入。怎么答：计数已为 0 时会变 -1 且滞留库里。追问：怎么在数据库层兜底？（`$max` 或条件更新）

### 5. 幂等：为什么点赞不用 toggle

假设接口设计成 `POST /like` 做**切换**：

- 用户手抖点两次 → 点赞又被取消了；
- 网络超时后客户端重试一次 → 同样把刚点的赞取消了。

而 `PUT /like`（点赞）和 `DELETE /like`（取消）是**幂等**的：
调用一次和调用十次结果完全一样，重试是安全的。

> 判断标准：**这个操作重复执行一次，结果会变吗？**
> 会变 → 不该用可重试的语义表达它。

#### 实现方法

本项目点赞用 `PUT /like`（点赞）、`DELETE /like`（取消），语义幂等；前端按"我想达成什么状态"调用，而不是切换。401 静默续期重放请求时，幂等接口重试安全。

#### 原理

若设计成 `POST /like` 做切换，用户手抖点两次会取消刚点的赞，网络超时重试一次也会把赞撤销。而 `PUT`/`DELETE` 调用一次和十次结果一样，重试安全。判断标准：操作重复执行一次结果是否变？会变就不该用可重试语义表达。

#### 与相关技术栈的关系

和 REST 的幂等约定一致：GET、PUT、DELETE 幂等，POST 不保证。和"乐观更新"配合时，前端本就持有目标状态，用幂等接口正好契合。和事件溯源（把每个动作记成事件）相比，本项目用幂等 HTTP 语义更轻。重试中间件、网络重发都依赖接口幂等才安全。

#### 面试常见问题与解题思路

**Q1：什么是幂等？为什么点赞接口要幂等？**
怎么想：从"重试安全"切入。怎么答：重复执行结果不变；点赞若用 toggle，重试会把赞撤销。追问：哪些 HTTP 方法天然幂等？

**Q2：怎么设计幂等的写接口？**
怎么想：从"目标状态"切入。怎么答：用 PUT/DELETE 表达"设为某状态"，或在请求里带去重键；避免用"切换"语义。追问：POST 怎么做成幂等？（客户端幂等键加服务端去重）

前端因此需要知道"我想达成什么状态"，而不是"切换一下"。
这反而让交互逻辑更清晰 —— 乐观更新时它本来就是知道目标状态的。

### 6. 复合索引的前缀复用

`{ postId: 1, userId: 1 }` 因为 `postId` 是**前导字段**，
所以它同时能服务"查某帖的所有点赞"这类只用 `postId` 的查询。
因此**不需要**再单独建一个 `{ postId: 1 }` 索引 —— 那是纯浪费。

规则：`{ a: 1, b: 1 }` 能服务 `a` 和 `a + b`，但服务不了单独的 `b`。

#### 实现方法

本项目在 `{ postId: 1, userId: 1 }` 上建唯一复合索引，因为 `postId` 是前导字段，它同时也能服务"查某帖所有点赞"这类只用 `postId` 的查询，所以不再单独建 `{ postId: 1 }`。

#### 原理

复合索引满足最左前缀：`{ a, b }` 能服务 `a` 和 `a + b`，但服务不了单独的 `b`。所以 `{ postId, userId }` 已覆盖"按帖子查点赞"的需求，再建一个 `{ postId }` 纯属浪费，只会占空间、拖慢写入。

#### 与相关技术栈的关系

和关系型联合索引的最左前缀原则完全一致。和"给每个查询字段都建单列索引"的直觉相比，复合索引能复用、更省。注意前缀复用是单向的：前导字段能单独用，非前导字段不能。设计索引时按查询的等值或排序顺序排字段。

#### 面试常见问题与解题思路

**Q1：复合索引为什么能省掉单列索引？**
怎么想：从"最左前缀"切入。怎么答：前导字段可被单独查询复用，所以 `{a,b}` 覆盖 `a`，无需再加 `{a}`。追问：反过来 `{b}` 能被复用吗？

**Q2：怎么给点赞查询设计索引？**
怎么想：从"查询模式"切入。怎么答：按 (postId,userId) 建唯一复合索引，既防重又支持按帖子查。追问：还要按时间范围查怎么办？（把时间作为复合索引后续字段）

## 三、代码走读

### `likes.service.ts` —— 幂等是怎么写出来的

`like()` 里没有"先查有没有赞过"，而是直接插入并捕获唯一索引冲突：

```ts
try {
  await this.likeModel.create({ postId, userId })
} catch (error) {
  if (!isDuplicateKeyError(error)) throw error
  // 冲突 = 已经赞过 = 目标状态已达成 → 返回成功，且**不重复计数**
  const counters = await this.postsService.getCounters(postId)
  return { liked: true, likeCount: counters?.likeCount ?? 0 }
}
```

注意冲突分支里**绝不能**再 `$inc` —— 否则快速连点就会把计数点出天际。

`unlike()` 同理：`deleteCount === 0` 说明本来就没赞过，
那也不该减计数（否则会把计数减成负数）。

### `posts.service.ts` —— `adjustCounter` 的管道更新

```ts
{ $set: { [field]: { $max: [0, { $add: [`$${field}`, delta] }] } } }
```

注意它是被**别的模块**调用的 —— 这正是 `PostsModule` 里
`exports: [PostsService]` 的用途。点赞模块不直接碰 `posts` 集合，
而是通过帖子模块暴露的语义明确的接口来改数据，
这样"帖子文档长什么样"依然只有帖子模块知道。

### 跨模块协作的依赖链

```text
CommentsModule ──imports──▶ PostsModule ──exports──▶ PostsService
LikesModule    ──imports──▶ PostsModule
```

如果 `PostsModule` 忘了写 `exports`，两个模块会**同时**在启动时报
`Nest can't resolve dependencies of the CommentsService (..., ?)`。
那个 `?` 就是在说"这个位置我找不到可注入的东西"。

> 删除"看起来没被用到"的 `exports` 时，一定要先想清楚
> 有没有别的模块在依赖它。

### 一个诚实的说明：三步操作不是原子的

`CommentsService.create()` 做了三件事：

1. 校验帖子存在；
2. 写入评论；
3. 原子增加帖子的评论计数。

**这三步不是原子的。** 如果第 3 步失败，评论已经写进去了，
但计数没涨 —— 数据会不一致。

彻底解决需要数据库事务（MongoDB 副本集支持，Atlas M0 也支持）。
本项目没用事务，理由是：

- 计数是**展示用的派生数据**，偶发偏差不影响业务正确性；
- 引入事务会给这个教学项目增加一层不必要的心智负担。

**但你要知道这个缺口在哪，以及生产环境下该怎么补。**

### 重构时机：第二个使用者出现时

阶段 3 时"内嵌作者快照"只属于帖子，写在 `post.schema.ts` 里就够了。
阶段 6 加评论时，"评论也要显示作者名"是同一个需求 ——
于是把它提到了 `common/schemas/author.schema.ts`。

同一阶段还提取了 `common/utils/mongo-errors.ts`（第二个用它的地方是点赞）。

> 判断该不该抽取的信号：**第二个使用者出现的时候。**
> 只有一个使用者时提前抽，只是把代码拆到两个文件里，反而更难读。

## 四、踩坑记录

### 坑 1 · `$inc: -1` 会把计数减成负数

取消点赞时如果直接 `$inc: { likeCount: -1 }`，而计数恰好是 0，
它就会变成 -1 —— 而且**永远留在数据库里**，界面上显示"-1"个赞。

修复是用聚合管道里的 `$max: [0, ...]` 在数据库层兜底。
这不是"多加一层保险"，而是**正确性的必要条件**：
应用层的判断在并发下不可靠，兜底只能放在能提供约束的那一层。

### 坑 2 · toggle 语义在重试下会翻转

最初打算用 `POST /like` 一个接口做切换，代码更少。
但很快意识到一个问题：**我们自己实现的 401 静默续期会重放请求**。

- 请求因为 Access Token 过期被拒（401）→ 刷新令牌 → 重放原请求；
- 这一次 401 时业务逻辑**还没执行**，所以重放是安全的 ✓。

但其它重放场景（网络超时重发、用户连点、将来可能加的重试中间件）
就没有这个保证了。对一个 toggle 接口，重放等于"撤销"。

改成 `PUT` / `DELETE` 之后，重放在语义上就是安全的。

> **一个接口设计上的问题，往往来自"调用方可能做什么"，而不是"它自己要做什么"。**

### 坑 3 · 复合索引前缀复用，不需要重复建索引

一开始给 `likes` 建了两个索引：
`{ postId: 1, userId: 1 }`（唯一）和 `{ postId: 1 }`。

第二个是多余的 —— 复合索引以 `postId` 为前导，本来就能服务只用 `postId` 的查询。
多余的索引会**占空间、拖慢写入**，而收益为零。

> 新手最常见的索引错误不是"没建索引"，而是"给每个字段都建了索引"。

### 坑 4 · ObjectId 不转字符串，前端会读到序列化包装

`_id` 和 `postId` 在数据库里是 ObjectId 对象。
如果 mapper 里直接返回 `doc._id`，经过 JSON 序列化后
前端拿到的可能是 `{}` 或 `{"$oid": "..."}` 这类包装，
表现就是"字段看着有，读出来是空的"。

所以 mapper 里对它们都显式做了 `String()` 转换。
**映射层的职责之一就是抹平存储类型与传输类型之间的差异。**

### 坑 5 · 幂等接口返回成功而不是 409

"已经赞过了"这种情况，最初想返回 `409 Conflict`。
但它其实是一个**成功的幂等结果** —— 用户想要的状态（已点赞）已经达成了。

返回 200 让客户端逻辑简单得多：不需要处理"这次算成功还是失败"，
乐观更新也不会被一个错误打断。

> 幂等接口的失败语义要谨慎设计：**"目标状态已达成"不是错误。**

## 六、术语表

| 术语 | 一句话解释 |
| --- | --- |
| 16MB 上限 | MongoDB 单个文档的硬上限，内嵌数组容易撞上 |
| 复合唯一索引 | 多个字段组成的唯一约束，可同时充当业务规则执行者 |
| 索引前缀 | 复合索引的前几个字段可被单独使用，复用同一个索引 |
| 原子更新 | 由数据库保证不可分割的更新，如 `$inc` |
| 聚合管道更新 | 用 `[ { $set: ... } ]` 形式在数据库内完成计算 |
| 幂等 | 重复执行结果不变，因而重试是安全的 |
| 读改写竞态 | "读 → 算 → 写"三步之间的窗口导致丢失更新 |
| 派生数据 | 可由其它数据算出的展示字段，如计数 |
| 降级 | 次要功能失败时不让主要功能受影响 |
| TOCTOU | 检查时与使用时不一致，导致权限绕过 |
