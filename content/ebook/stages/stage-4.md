## 二、核心概念

### 1. 跨域到底是怎么回事

这是联调时最容易被卡住、报错又最难看懂的一件事。

**同源策略**规定：来自 `http://localhost:3001` 的页面，
不能读取 `http://localhost:3000` 的响应 —— 协议、域名、端口
**三者有一个不同就算跨域**。注意：3000 和 3001 是**不同的源**。

关键点在于：**请求其实发出去了，后端也处理了，只是浏览器不让 JS 读结果。**

于是你会看到那个经典的迷惑现象：

```text
浏览器控制台：CORS policy: No 'Access-Control-Allow-Origin' header...
后端日志：    （什么都没有）
```

**后端日志一片空白，是因为请求根本没被视为"需要处理"，
或者处理了但浏览器不给看结果。** 所以排查跨域时不要盯着后端日志，
要盯浏览器的 Network 面板和 Console。

服务端要做的就是"明确表态允许谁"：

```ts
app.enableCors({
  origin: corsOrigin,      // 具体来源列表，不能是 '*'
  credentials: true,       // 允许携带 Cookie
})
```

`credentials: true` 和 `origin: '*'` **不能同时存在**。
因为"允许所有人"和"允许携带你的凭据"放在一起等于把凭据公开了。
浏览器会直接拒绝，报错信息同样很难懂。

#### 实现方法

本项目在后端 `main.ts` 调 `app.enableCors({ origin: corsOrigin, credentials: true })`，origin 是具体来源列表，不能是 `*`。`credentials: true` 和 `origin: '*'` 不能同时存在，否则浏览器直接拒绝。

#### 原理

同源策略规定协议、域名、端口三者有一个不同就算跨域。关键点：跨域请求其实发出去了、后端也处理了，只是浏览器不让 JS 读响应。所以 CORS 报错出现在浏览器 Console，后端日志一片空白。服务端用 `Access-Control-Allow-Origin` 等响应头明确表态允许谁。

#### 与相关技术栈的关系

CORS 是浏览器的安全机制，和后端语言无关，Node、Java、Go 都靠响应头解决。和同源部署（前后端放同一域名后反向代理）相比，CORS 适合前后端分离部署。和 `jsonp`（老式跨域技巧）相比，CORS 是标准方案、支持任意请求方法。注意非简单请求（带自定义头、非 GET/POST 等）会先发 `OPTIONS` 预检。

#### 面试常见问题与解题思路

**Q1：什么是同源策略？跨域是怎么产生的？**
怎么想：从"协议、域名、端口"切入。怎么答：三者任一不同即跨域；限制的是 JS 读取响应，请求本身通常发出去了。追问：为什么后端日志没有 CORS 错误的痕迹？

**Q2：怎么解决跨域？`credentials` 为什么不能和 `origin: '*'` 一起用？**
怎么想：从"凭据安全"切入。怎么答：后端开 CORS 并声明允许的来源；带凭据时必须是具体 origin，不能是 `*`，否则等于把凭据对所有人公开。追问：预检请求是什么？什么时候触发？

### 2. 环境变量注入前端：只在 `public` 里的才可见

```ts
runtimeConfig: {
  public: {
    apiBase: process.env.NUXT_PUBLIC_API_BASE || 'http://localhost:3000/api',
  },
}
```

`public` 里的东西**会被打包进浏览器可见的产物**。所以有一条硬规则：

> **任何以 `NUXT_PUBLIC_` 或 `PUBLIC_` 开头的东西，都绝不能放密钥。**

本项目的密钥（`MONGODB_URI`、`JWT_*`、`NVNIM_API_KEY`、`GITHUB_TOKEN`）全部只在
`apps/api/.env` 里，前端一个都碰不到。这不是巧合，是**架构上就隔开了**。

顺带说：为什么用 `runtimeConfig` 而不是直接写常量？
因为阶段 8 部署时后端地址会变。用 `runtimeConfig` 的话，
**只改一个环境变量，不动代码**。

#### 实现方法

本项目用 Nuxt 的 `runtimeConfig.public.apiBase` 暴露前端可见的配置，值取自 `NUXT_PUBLIC_API_BASE`，缺省回退到 `http://localhost:3000/api`。密钥（`MONGODB_URI`、`JWT_*`、`NVNIM_API_KEY`）只在 `apps/api/.env`，前端碰不到。

#### 原理

`runtimeConfig.public` 里的变量在构建或运行时被打包进浏览器可见的产物，所以任何以 `NUXT_PUBLIC_` 或 `PUBLIC_` 开头的环境变量绝不能放密钥。用 `runtimeConfig` 而不是写死常量，是因为部署时后端地址会变，只改一个环境变量就能切换，不动代码。

#### 与相关技术栈的关系

和 Vite 的 `import.meta.env`（`.env` 中以 `VITE_` 前缀暴露）是同一思路：前缀决定可见性。和把配置写进源码常量相比，`runtimeConfig` 支持运行时注入，适合多环境部署。和服务端私有配置（`runtimeConfig` 非 public 部分）相比，public 部分是唯一能进浏览器的那一半。

#### 面试常见问题与解题思路

**Q1：前端环境变量为什么不能放密钥？**
怎么想：从"打包产物可见"切入。怎么答：public 前缀的变量会进浏览器 JS，任何人都能看到；密钥必须只在服务端。追问：那前端要调需要密钥的第三方 API 怎么办？（走后端代理）

**Q2：runtimeConfig 和写死常量有什么区别？**
怎么想：从"多环境部署"切入。怎么答：runtimeConfig 支持运行时按环境变量覆盖，不重新构建就能换地址；常量要改代码重新打包。追问：SSR 下 runtimeConfig 的 public 和 secret 分别什么时候可用？

### 3. 错误归一化：为什么要有 `useApi`

后端已经把所有错误压成了 `ApiErrorBody` 一种形状（阶段 3 的全局过滤器）。
但前端拿到的**错误对象**形状仍然很别扭：

```ts
// ofetch 抛出来的错误长这样
error.response.status      // 状态码
error.response._data       // 已解析的响应体（注意这个反直觉的下划线）
```

如果每个调用处都去解这层结构，你会写十遍同样的代码，
而且总会漏掉几个 `response` 不存在的分支（网络层失败时它就没有）。

`useApi` 把它压成一个类：

```ts
class ApiRequestError extends Error {
  statusCode: number
  details?: string[]
  get isNetworkError(): boolean { return this.statusCode === 0 }
}
```

于是调用方只需要认识三个概念，而不是一堆可选链。

#### 实现方法

后端已在阶段 3 把所有错误压成 `ApiErrorBody` 一种形状。前端 `useApi` 再把 ofetch 抛出、结构别扭的错误（`error.response.status`、`error.response._data`）封装成 `ApiRequestError extends Error`，带 `statusCode`、`details?`、`isNetworkError`。调用方只需认识这三个概念。

#### 原理

ofetch 的错误对象为了兼容各种失败形态，字段嵌套且部分可选（网络层失败时 `response` 不存在）。如果不归一化，每个调用处都要重复解这层结构并补 `response` 判空，容易漏分支。封装成统一错误类后，调用方用一套语义（状态码、详情、是否网络错误）处理所有失败。

#### 与相关技术栈的关系

和 axios 的拦截器（`responseInterceptor` 统一加工错误）思路一致；和 React Query、SWR 的 `error` 对象相比，本项目手动归一成自定义类更贴合 Nuxt 组合式风格。和直接 `try/catch` 裸抛相比，归一化让错误在 UI 层有稳定形状，便于统一展示与重试。

#### 面试常见问题与解题思路

**Q1：为什么前端也要做错误归一化？**
怎么想：从"稳定形状"切入。怎么答：底层 HTTP 库的错误结构嵌套且可选，每个调用处重复解构易出错；归一化后 UI 只需处理统一语义。追问：怎么区分网络错误和业务错误？

**Q2：怎么区分网络故障和业务错误？**
怎么想：从"状态码"切入。怎么答：网络层失败没有响应（statusCode 记 0 或噪声），业务错误有 HTTP 状态码和 `ApiErrorBody`。追问：401 应该走重试还是登出？

### 4. "网络故障"与"业务结果"必须分开

这是本阶段我**自己踩到并修掉**的一个真实缺陷。

一开始详情页的逻辑是"拿不到帖子 → 显示找不到"。看起来没问题，
但后端没启动时，它也会显示"找不到这篇文章" ——
**用户会以为文章被删了，于是跑去别处找，而实际上只是服务没开。**

正确做法是把三种情况分开：

| 情况 | 状态码 | 用户看到 | HTTP 响应码 |
| --- | --- | --- | --- |
| 帖子确实不存在 | 404 | "找不到这篇文章" | 404 |
| 后端挂了 / 断网 | 0 | "暂时打不开这篇文章"+ 重试 | 200 |
| 服务端出错 | 5xx | 同上 + 重试 | 200 |

> **代码写完了，不等于这些分支你想过。** 这也是为什么本阶段的验收清单
> 里有一半是"故意弄坏"。

#### 实现方法

本项目把详情页的三种情况分开：帖子真不存在返回 404、显示"找不到这篇文章"；后端挂了或断网（statusCode 0）显示"暂时打不开这篇文章"加重试；服务端 5xx 同样给可重试提示。验收清单专门要求"故意关掉后端"来暴露没分开的 bug。

#### 原理

"拿不到帖子"不等于"帖子被删了"。后端没启动时也拿不到，但若显示"找不到"，用户会误以为文章没了。把网络或服务端失败和"资源不存在"区分开，是正确地向用户传达失败原因的前提，也决定了要不要提供重试。

#### 与相关技术栈的关系

和"乐观更新加失败回滚"的错误处理互补：乐观更新关注写操作失败如何回退，这里关注读操作失败如何分类呈现。和只用 `loading`/`error` 布尔相比，按状态码或错误类型分流能给出更精确的文案与动作（重试还是放弃）。和全局错误边界（如 error.vue）结合，可把未归一化的意外错误兜底。

#### 面试常见问题与解题思路

**Q1：前端怎么区分"资源不存在"和"服务挂了"？**
怎么想：从"HTTP 语义"切入。怎么答：靠状态码，404 表示资源不存在，0 或网络异常、5xx 表示服务端或网络问题；文案和重试策略因此不同。追问：为什么不能都显示"加载失败"？

**Q2：为什么验收要"故意弄坏"系统？**
怎么想：从"分支覆盖"切入。怎么答：正常流程验证不了错误分支，只有主动关后端、断网才能确认失败路径做了正确区分与提示。追问：还有哪些异常路径容易被忽略？（超时、部分成功）

## 三、代码走读

### `app/composables/useApi.ts`

它统一了四件事：

1. **基地址**：来自 `runtimeConfig`，可用环境变量覆盖；
2. **错误归一化**：任何失败都变成 `ApiRequestError`；
3. **JSON 处理**：`$fetch` 已经做了，集中在这里避免有人再写一处 `res.json()`；
4. **（阶段 5 会加）** 鉴权头与 401 静默续期。

还有一个容易被忽略的约束，写在注释里但值得重复：

> `useApi()` **必须在 Nuxt 上下文里调用**（组件 setup、store setup、插件中）。
> 因为它内部要用 `useRuntimeConfig()`。本项目在 store 的 setup 阶段
> 调用一次，后面的函数通过闭包共享 —— 这样就不会在异步 action 里
> 撞上 "nuxt instance unavailable" 这种极难定位的错。

### `app/stores/post.ts` —— 这次替换只改了一个文件

阶段 2 到这里，数据源从 mock 换成了真实接口，而改动**全部发生在这一个文件里**。

页面、组件、对外的状态与动作，一个都没变。这是阶段 2 把数据源
收口在少数几个函数里的回报：

```text
阶段 2：读到 mockPosts
阶段 4：改成 api.get('/posts', query)
        ↑ 只改这里
```

如果你当初在 `PostCard.vue`、`index.vue`、`[id].vue` 里各写一处
`import { mockPosts }`，这次就要改四个文件，而且必然会漏一个。

### 契约校验的实证

用 LSP 的"查找引用"看 `packages/shared` 里的 `Post` 类型，得到 17 处引用、
分布在 5 个文件：

```text
packages/shared/src/types/post.ts          定义
apps/api/.../posts.service.ts              4 处
apps/api/.../posts.controller.ts           4 处
apps/api/.../posts.mapper.ts               2 处
apps/web/app/stores/post.ts                5 处
```

再用"全仓符号搜索"查 `PostListResponse`，结果是 **1 个文件**。

这两个数字合起来说明一件事：**前后端引用的是同一个类型定义，没有第二份。**
这就是阶段 1 那个 `packages/shared` 目录存在的全部意义 ——
它把一个流程口号变成了可被工具验证的事实。

## 四、踩坑记录

### 坑 1 · 把网络故障误报成 404（自己写出来的 bug）

见上文"网络故障与业务结果必须分开"。这个 bug 的危险之处是
**界面看起来完全正常**，只是文案在骗人。

发现它的方式不是"测试正常流程"，而是**故意把后端关掉**。

### 坑 2 · ofetch 的响应体藏在 `response._data`

```ts
error.response._data    // ✅ 已解析的响应体
error.data              // ❌ undefined
```

这个下划线前缀很反直觉。不知道它，你就会写出
"后端明明返回了 message，前端却拿不到"这种卡半天的代码。

### 坑 3 · CORS 报错永远出现在浏览器端

后端日志什么都没有，Console 里却是红的。
排查顺序应该是：

```text
1. Network 面板 → 这个请求发出去了吗？状态码是多少？
2. Console → 具体是哪一条 CORS 规则被拒？
3. 后端 main.ts → origin 列表里有当前地址吗？credentials 和 origin 冲突吗？
```

不要一上来就改后端代码 —— 大概率你改的地方根本不在问题路径上。

### 坑 4 · Nuxt 上下文丢失

`useRuntimeConfig()`、`useState()`、`useNuxtApp()` 这类 API
**必须在 Nuxt 上下文里调用**。在异步回调、`setTimeout`、
或者独立的工具函数里调用它们，会报 "nuxt instance unavailable"。

本项目的做法是在 store 的 setup 阶段把 `useApi()` 的结果存下来，
后续通过闭包使用。

## 六、术语表

| 同源 | 协议 + 域名 + 端口三者完全相同 |
